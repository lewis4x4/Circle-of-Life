# Facility Launch Center — Onboarding UX Review (M15, M18, and the patterns behind them)

**Date:** 2026-05-05
**Scope:** `src/app.js`, `src/intakeCatalog.js` (with cross-checks against `src/state.js`, `src/scoring.js`, `styles.css`)
**Mode:** Read-only review. No source files modified.
**Author:** JARVIS

---

## Context / Scope

The user reported two onboarding-UX defects:

1. **M15 (Family / Responsible-Party Portal)** — the "Family contact" form forces operators to *type* a resident's name as free text instead of selecting/linking an existing resident.
2. **M18 (Vendors / Contacts / Emergency)** — the checklist row at the top of the module renders as **pill-shaped chips** that look like interactive buttons, but they do nothing on click.

Both issues are not local; they are symptoms of two cross-cutting patterns in the intake renderer:

- `renderRecordForm` / `renderEditableRecordCells` blindly emit `<input type="text">` for every `field` in a collection, including for foreign-key fields like `residentName`. There is no concept of a "lookup field" in the catalog spec.
- `renderIntakeChecklist` emits `<li>` chips inside `.checklist-grid` (`styles.css:78–79`), styled with rounded corners, border, fill, and `font-weight: 750`. The visual treatment screams "button," but no click handler is wired in `app.js` and the items are not part of the completeness model in `scoring.js`.

This review prescribes fixes for both, prioritized for immediate implementation, and notes the four other modules where the same fixes apply by extension.

---

## Findings

### Finding 1 — Resident references are free-text strings, not links (affects M6, M7, M10, M11, M15)

**Where it lives**

- `intakeCatalog.js:218` — `M15.familyContacts.fields[0]: { key: "residentName", label: "Resident" }`
- The same field key `residentName` is used as a typed-string foreign key in:
  - `M6.rateRecords` (line 38)
  - `M7.carePlans` (line 58)
  - `M10.medicationProfiles` (line 118)
  - `M11.dietaryProfiles` (line 138)
- Meanwhile the canonical roster is at `state.mvpData.M5.residents[*]`, with a stable `id`, `fullLegalName`, `preferredName`, and `roomBed` (`intakeCatalog.js:11–18`, `state.js:181–204`).

**Why it's broken UX**

- An operator must remember exact spelling to "link" a record across modules; there is no auto-complete and no validation against M5.
- "Evelyn Carter" in M15 vs `"Evelyn Carter "` (trailing space) in M6 silently fragments the resident's record across the binder.
- M5 cannot ever say *"Evelyn has 3 family contacts, 1 rate record, 1 care plan, 1 med profile, 1 diet profile"* — the data model exists, the UI is just not joining on it.
- Add-resident-first-then-document-them is an obvious workflow today, but the UI does not enforce it. A new operator will type "Mrs. Carter" three times in three modules and then wonder why the rollup is empty.
- This contradicts the explicit M5 framing in `intakeCatalog.js:4`: "every workflow knows who lives in the building."

**Severity:** Blocks "single source of truth for the resident" — which is the whole launch claim of M5. P0.

### Finding 2 — Checklist chips look like buttons but are inert (affects every intake module)

**Where it lives**

- `app.js:253–255` — `renderIntakeChecklist` returns `<ul class="checklist-grid">{<li>…</li>}</ul>`.
- `styles.css:78–79` — pill styling (`border-radius: 999px`, `border`, `background: #f8faff`, `font-weight: 750`, `color: #26345f`). This is **chip/button styling**, not list-item styling.
- No `data-*` attribute, no event delegation, no state hook. The items never enter `state.mvpData` and never affect `scoring.js`.

**Why it's broken UX**

- Affordance lies: the user clicks "Vendor directory," "After-hours process," etc. and gets nothing. Every senior operator I've watched do this kind of intake will click these on first contact.
- The checklist is presented as the **scope of the module** ("Capture vendors, emergency contacts, utilities, service agreements, after-hours routing, and operational dependencies" — `intakeCatalog.js:243`). If the user can't mark them off, they have no way to know whether a single vendor record is *enough* to satisfy "After-hours process" — which is a different topic than "Vendor directory."
- The completeness % shown on the scorecards (`renderIntakeCoverageSummary`) is computed only from the scalar `fields` and the existence of any rows in collections (`scoring.js:108–113`). Two vendor rows can score 100% complete while leaving "Insurance requirements" and "Account numbers" entirely unrepresented.

**Severity:** Highest-frequency UX trap in the app. P0 — fix simultaneously with Finding 1 because both touch every intake module.

## Recommendations (prioritized)

### P0-A — Add a typed lookup field to the catalog and resolve M15 + 4 cousins in one pass

**Catalog model change.** Introduce a typed field descriptor in `intakeCatalog.js` so the renderer knows when to emit a picker instead of a free input. New shape, additive only:

```js
{
  key: "residentId",                    // store the FK
  label: "Resident",
  lookup: {
    sourceModule: "M5",
    sourceCollection: "residents",
    valueField: "id",
    labelTemplate: "{preferredName} ({roomBed})", // or fullLegalName fallback
    secondaryField: "fullLegalName",
    addNewHref: "module-M5"             // deep-link to "Add resident" if not found
  },
  denormalize: ["residentName"]         // copy display name onto the record for offline/export
}
```

Apply to: `M6.rateRecords`, `M7.carePlans`, `M10.medicationProfiles`, `M11.dietaryProfiles`, `M15.familyContacts`.

**Renderer change in `app.js`** — extend `renderRecordForm` and `renderEditableRecordCells` to branch on `field.lookup`. For a lookup field render a **combobox**:

- A native `<input list="residents-M5">` + `<datalist>` populated from `state.mvpData.M5.residents`. This is the pragmatic choice — zero extra dependencies, native keyboard support, works on mobile, and the static-app constraint is preserved.
- Display the picked label; on submit, resolve back to the resident `id` and persist both `residentId` (canonical link) and `residentName` (denormalized display, for export and legacy compatibility).
- If the typed value doesn't match a roster row, show a soft inline warning **next to the field**: *"Not in M5 roster yet — Add resident first."* with a button that scrolls to the M5 add-resident form. Do **not** silently accept unmatched names; that is exactly the failure mode today.
- For empty rosters, the field should be disabled with helper text *"Add at least one resident in M5 before linking family contacts here."* This makes the workflow obvious.

**Reverse-link UX in M5 (small but high-impact addition).** On each M5 resident row, render compact rollup badges:

> 👨‍👩‍👧 2 contacts · 💵 1 rate · 🩺 1 care plan · 💊 1 med · 🍽 1 diet

Computed by counting rows in M6/M7/M10/M11/M15 that match `residentId`. Click a badge → expand the rollup inline (or scroll to the matching module). This single change converts M5 from "another data table" into the **resident binder index** the spec promises (`intakeCatalog.js:4`).

**Validation in `scoring.js`.** A family contact (or rate, care plan, etc.) without a valid `residentId` should not count toward completeness. Update `requiredRecordComplete` to treat lookup fields as "present only if the FK resolves to a real M5 row." This naturally raises the bar for completeness without adding new UI.

**Why this is P0-A.** It's one renderer branch + one catalog field shape. Five modules become correctly linked. The resident binder finally exists. No new dependencies, no new screens.

### P0-B — Make the checklist chips actually mean something

The chips signal scope. Pick one of two postures:

#### Option B1 (recommended) — Promote them to a "Topics confirmed" tracker

Make each chip a **toggle button** with explicit state. Persist per-module checklist coverage in `state.mvpData[code].topicsConfirmed = { "Vendor directory": true, "After-hours process": false, ... }`.

Visual treatment (additive, in `styles.css`):

- Default: outlined chip, `cursor: pointer`, hover lift. Add a `+` icon to signal "open."
- Confirmed: filled chip with a leading `✓`, accent color (`#16a34a` background or border), no longer reads as "missing."
- Add a small caption above the row: **"Topics confirmed: 3 / 7"** with a green progress bar.

Click handler in `app.js` event delegation:

```js
const topic = e.target.closest("[data-topic-toggle]");
if (topic) {
  const code = topic.dataset.module;
  const item = topic.dataset.topic;
  state = toggleIntakeTopic(state, code, item); // new state.js helper
  render();
  return;
}
```

Wire into `scoring.js`. In `getCatalogCompleteness`, append a check `pct(spec.checklist.map(t => Boolean(data?.topicsConfirmed?.[t])))` and weight it ~25% of the module completeness. This means an operator can no longer green-light a module with one collection row and zero scope confirmation.

Add a tooltip: *"Confirms this topic is captured somewhere in this module's data, or has been deliberately scoped out for launch."*

This makes the chips **earn their button affordance** instead of denying it. It also gives the operator a satisfying click-and-tick rhythm during intake — which is the kind of small reward that moves long forms from "spreadsheet purgatory" to "checklist competence."

#### Option B2 (fallback if B1 is too much for this sprint) — Demote them to non-interactive labels

If you can't ship the toggle in the same pass, change the visual treatment so they stop pretending. In `styles.css`:

```css
.checklist-grid { gap: .35rem; }
.checklist-grid li {
  border: none;
  background: transparent;
  border-radius: 0;
  padding: 0;
  font-weight: 500;
  color: #475569;
}
.checklist-grid li::before { content: "▸ "; color: #94a3b8; }
```

And in `app.js` add a tiny header above the list: *"What this module captures (informational scope)"* so the operator stops looking for an action there.

This is strictly inferior — the checklist *should* be active — but it stops the daily false-affordance frustration in the meantime.

### P1 — Two smaller compounding fixes for the same modules

These don't require new mental models, but they remove the rest of the "type-it-again" frustration in M15:

**P1-A. Auto-fill family contact from M5 responsible-party.** When the operator picks a resident in M15, pre-fill the form with the parsed `responsibleParty` and `emergencyContact` strings from M5 (split on `/` and digit groups — they already follow the convention `"Mark Carter / son / 205-555-2100"`). The operator confirms or edits. This eliminates ~70% of typing on M15 in practice.

**P1-B. Inline "Add resident" affordance from any lookup.** If the operator types a name that doesn't match, show *"+ Add 'Mrs. Carter' to M5 roster"*. Clicking it opens a tiny inline minimalresident form (full legal name + room/bed + status), saves it via `addModuleRecord(state, "M5", "residents", …)`, and immediately back-fills the lookup with the new ID. This means the operator never has to leave M15 to fix the missing-resident case — a real day-of-launch optimization.

---

### P2 — Polish that pays off across all modules

These are not blockers but they round out the M15/M18 fix and apply to every intake module:

1. **Promote the checklist row above the scalar fields visually.** Right now the order in `renderOperationalIntakeModules` is fields, then collection. The checklist comes from `module-intro` but it sits below the lead paragraph in plain text density. Once the chips are interactive (B1), give them their own card with the "Topics confirmed: X / Y" header and progress, so operators see scope progress at a glance.
2. **Sticky module summary.** Each `<details open class="intake-module">` summary already shows completeness %. Add: count of collection rows, count of topics confirmed, and an inline pulse if any required field on any row is blank. Cheap, fast, very motivating.
3. **Lookup pickers should also be added to admissions → resident transition.** When an `M14.admissionsPipeline` row's stage flips to "Moved in," prompt the operator: *"Promote prospect 'Robert Allen' to the M5 resident roster?"* — preserving the `prospectName → fullLegalName` linkage. Closes the loop between sales and census.
4. **Don't leave `residentName` orphaned during migration.** During the lookup rollout, keep `residentName` in the schema as a denormalized echo of the picked resident; that way export markdown and the JSON dump (`buildReadinessMarkdown`, `buildStateJsonExport`) keep working unchanged.

## Acceptance Criteria

The fixes are working when an operator can:

1. **Open M15**, click the Resident field, and see a list of M5 residents (or a clear "no residents yet — go to M5" disabled state). Typing "Ev" narrows the list. Picking "Evelyn Carter" populates the form and the persisted record carries both `residentId` and `residentName`.
2. **Open M5**, see *"👨‍👩‍👧 2"* on Evelyn's row, click it, and see the two M15 family contacts inline.
3. **Open M18**, see "Topics confirmed: 0 / 7" and a row of clickable outlined chips. Click "Vendor directory" → it fills in green with a ✓, the count updates to 1 / 7, the module completeness on the scorecard moves up. Refresh the page → the state persists.
4. **The same patterns work** in M6, M7, M10, M11 (resident lookup) and across every intake module's checklist (topic toggles).
5. **No regressions** in markdown/JSON export — `residentName` is still present on every record because of denormalization.

## Notes on what I deliberately did *not* recommend

- **A full search/typeahead component** with fuzzy matching, virtual scrolling, etc. The native `<datalist>` covers the realistic resident counts (≤ ~150) and keeps the static-app posture. Revisit only if rosters cross several hundred.
- **A separate "Resident Binder" tab.** The reverse-link badges on M5 + module-level lookups produce the same outcome with less surface area. Adding a tab would be premature.
- **Custom modal libraries.** The inline "Add resident" affordance in P1-B is a small inline form, not a modal — fewer moving parts, less framework.
- **Editing the chips' text content.** The current checklist labels are fine as scope topics. Their *behavior* is the bug, not their wording.
