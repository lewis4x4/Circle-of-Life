## Authority and lifecycle contract

Forward migration **327** adds a service-only lifecycle command/outbox. Migration 326 remains unchanged. A restrictive command commits the profile/facility restriction, a strictly advancing authorization version, required audit row, and durable synchronization job atomically. Repeating the same request key returns the same receipt; reusing it for another actor, organization, or payload fails. A fresh disable command also fences a previously prepared reactivation even when the profile was already disabled.

Expansions first record an authorized intent and exact expected/reserved target versions without changing profile authority. The worker takes a bounded lease, revalidates the current actor/session and target version, prepares Auth metadata, revalidates again, records provider success, then atomically applies database expansion and its audit. Finalization holds current profile, Auth session, and facility locks. Changed target/actor authority terminally cancels stale expansion; stale retries cannot authorize a broader role or restore facility access. A failed audit rolls back the database mutation. Supabase Auth is outside the PostgreSQL transaction, so an interrupted provider update can leave metadata temporarily inconsistent; database profile/session/version checks remain authoritative throughout.

`netlify/functions/user-auth-sync.ts` consumes one pending job every five minutes, with per-request timeouts, a 25-second invocation deadline, and a 300-second lease shared across jobs for the same target. Expired leases resume, retries use the same idempotent desired Auth update, and failures have bounded backoff and eight-attempt dead-letter handling. A permanent indexed registry covers only lifecycle-touched targets. Each tick checks at most 20 oldest targets against actual Auth role, organization, version, and ban state; mismatch creates a current-profile reconciliation job. Successful and late/failed provider completions request another observation, regardless of lease ownership. The periodic bounded check also catches a remote write that finishes after local timeout, process death, and an earlier completed repair. Pending jobs retain ownership of their desired state; reconciliation never grants profile authority. Success/finalization and status reads verify observed Auth state, so a historical completed job cannot hide current drift. Reconciliation repairs bans and only provenance-proven obsolete own bans after a finalized explicit reactivation. Provider metadata records a separate ban job/version only when a call changes ban status. Ordinary role/facility updates preserve independent Auth/security holds; those holds require explicit operator review and report action_required. Negative regressions ensure neither ordinary expansions nor the registry silently unban a current independent hold. The scheduled function exports Netlify's native schedule configuration and cannot be invoked as a public HTTP endpoint. Job payloads are inaccessible directly to public, anonymous, authenticated, and service roles; narrow definer RPCs own access. Stored failures contain codes only. The user-detail API exposes pending/finalized status after its current actor and target-scope checks. Pending operations return HTTP 202; controls describe them as pending rather than completed.

The legacy `/hard-delete` URL now **retires sign-in access**, preserving Auth identity, the profile, memberships, clinical/staff/financial records, and attribution. It no longer attempts FK-blocked physical deletion or deletes account-reference rows before provider success. Owner confirmation remains required. UI copy explicitly says that identity/history remain and an authorized administrator can reactivate the account with explicitly chosen access. This operation is reversible through that restoration flow, not physical erasure.

Facility grant/revoke routes now reach atomic command receipt handling before mutable grant preconditions. The missing `/facility-access/[facilityId]` child route exists and validates IDs (SYS-008). The editor persists selected grants, revokes, and primary-facility changes; it excludes revoked historical grants from current selections. Replacement grants synchronize before removals so a transfer does not accidentally disable the account. A partial/pending sequence stops and refreshes actual persisted scope.

Proxy, `HavenAuthProvider`, shared client-role resolution, and the legacy `useAuth` compatibility facade consume current database role/organization. The facade no longer exposes stale JWT roles to administrator controls. Migration 327 also repairs nullable fail-open checks identified during independent review: unmanaged onboarding version checks, rounding claim/grant/assignment checks, and operation completion/defer assignment checks.
