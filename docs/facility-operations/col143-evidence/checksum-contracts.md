# COL-143 amendment: trusted checksum verification (source-only)

Settled 2026-09-10. The committed 343 records a client-declared SHA-256 and compares two client-supplied strings at finalization; that is not verification of the uploaded bytes (OWNER-DECISIONS 3f(ii) deferred it to the hosted step). This amendment resolves the mechanism in source on `codex/hfo-col143-evidence` by editing `343_hfo_verified_evidence.sql` in place (provisional, unapplied anywhere), its probe, the evidence library and routes. The hosted Storage proof (acceptance item 3) stays open and gains one confirmation step.

## 1. Trust anchor

The only content fingerprint in the database that the client did not write is the Storage service's `metadata->>'eTag'` on `storage.objects`, which for a single-request upload of at most twenty mebibytes is the MD5 of the stored bytes. **Precondition:** this holds only while `storage.objects` is written by the Storage service alone. A direct `INSERT` into `storage.objects` with a crafted eTag would pass the bucket's insert policy (the policy decides who may write a path, not what the metadata says), which is harmless only because the `storage` schema is not exposed through the project's Data API (PostgREST exposes `public` and `graphql_public`); the hosted proof (§6) confirms that exposure list and stops if `storage` is exposed. The client therefore declares the file's MD5 (computed in the browser from the bytes it is about to upload) and the database verifies it against the object's eTag, twice: when the row is marked uploaded and again at finalization. The declared SHA-256 stays optional and informational. Whether the hosted eTag is a plain MD5 for signed-URL uploads is the confirmation step added to the hosted proof; if it is not, the recorded fallback is an app-tier verifier that streams the object through the session's signed URL and presents the hash under a database-held secret, and nothing finalizes until one of the two mechanisms is proven.

## 2. Schema changes (343 in place)

- `operation_evidence.declared_md5 text` — 32 lowercase hex; NOT NULL for object kinds, NULL for `linked_record` (shape CHECK extended).
- `checksum_method text` (`storage_etag_md5`), `checksum_verified_at timestamptz` — set together with the existing `checksum_verified=true`; NULL otherwise. CHECK: a finalized object row has `checksum_verified=true` with method and instant.
- `object_version text` — from `storage.objects.version` when the column exists on the replay target (add `version text` to `scripts/pg-verify-stub.sql`); recorded at uploaded, re-checked at finalization.
- Unique `(receipt_id, declared_md5) WHERE state='finalized'` beside the SHA-256 dedupe; prepare replays `Evidence already finalized for these bytes` on either.

## 3. Verification rule (`haven.operation_evidence_object` and the two commands)

- **Normalise** the eTag: strip surrounding quotes and any weak prefix, lower-case. A 32-hex value is an MD5; a value with a `-N` suffix is a multipart fingerprint; anything else is unknown.
- **At `mark_uploaded`** (and at finalization from `prepared`): object present at the owned path, owned by the uploader, size and mime equal to the declared values (as today), then checksum: eTag MD5 ≠ `declared_md5` → the row is moved to `failed` with `failure_reason='checksum_mismatch'` and a `failed` event whose details carry the declared and observed values, inside the same transaction, and the command **returns** the failed row (no exception, so the failure is durable) — the reply carries `outcome: 'checksum_mismatch'`; a matching MD5 records `object_id`, `object_etag`, `object_version`, `checksum_verified=true`, method and instant. An eTag that is not an MD5 leaves the row `uploaded` with `checksum_verified=false` and the reply says `outcome: 'checksum_unverifiable'`.
- **At `finalize`**: re-read the object by bucket and path and require `id = object_id`, eTag equal to `object_etag`, `version` equal to `object_version` when recorded, owner still the uploader, size and mime unchanged; any difference moves the row to `failed` with `failure_reason='object_changed'` and returns it (`outcome: 'object_changed'`). A row whose checksum is unverified is refused (`Evidence checksum could not be verified from the stored object`, P0001) and stays `uploaded`, so the uploader may fail it explicitly. Only a verified, identical object finalizes; satisfaction (343 §2.3) then runs unchanged.
- A re-formatted eTag (quotes, weak prefix or case changed) with the same normalised MD5 and the same object id and version still finalizes: the bytes are the same. Finalization straight from `prepared` observes the object once, under the upload rules above, so "verified twice" describes the uploaded-then-finalize path; the failed event of a finalization carries the expected receipt revision it was made under.
- A failed row attaches to nothing, blocks nothing and is retried with a new preparation (343 semantics).

## 4. Runtime

- `src/lib/operations/md5.ts`: MD5 (RFC 1321) in TypeScript with no dependency, incremental over `Uint8Array` chunks, `md5Hex(bytes)` and `md5OfBlob(blob, chunkSize)` for the browser; tests against the RFC test vectors and a multi-chunk equality check.
- `src/lib/operations/evidence.ts`: prepare payload requires `md5` (32 hex) for object kinds and keeps `sha256` optional; `EVIDENCE_SELECT` adds `declared_md5, checksum_method, checksum_verified_at, object_version`; reply mapping surfaces `outcome` (`uploaded` / `finalized` / `checksum_mismatch` / `checksum_unverifiable` / `object_changed`); the uploaded and finalize routes return 409 with class `conflict` and the failed evidence for a mismatch or a changed object, and 409 with class `uncertain` for an unverifiable checksum.
- Route and library tests updated; the download route unchanged.

## 5. Probe additions (`review_hfo_verified_evidence.sql`)

Fixtures insert `storage.objects` rows with `metadata.eTag` set to the quoted MD5 of a known byte string. Matched MD5 → uploaded with `checksum_verified`, method and instant; finalized. Mismatch at uploaded → row `failed` with `checksum_mismatch`, `failed` event with both values, receipt still `missing`, later prepare with a new key proceeds. Mismatch at finalization (eTag changed between uploaded and finalize) → `object_changed`. Object id replaced under the same path → `object_changed`. Multipart eTag → uploaded unverified, finalize refused, row stays `uploaded`, explicit fail works. Missing `md5` on an object kind refused at prepare; `md5` on a linked record refused. Duplicate finalized MD5 on the same receipt replays the existing id. Every previous assertion passes with `md5` added to the fixtures.

## 6. Hosted proof step added (COL-143-HANDOFF)

Before any upload, confirm `storage` is absent from the project's exposed API schemas (Settings → API → Exposed schemas; expected `public, graphql_public`); if it is present, stop, because a client could then write `storage.objects` metadata directly and the eTag would not be a trust anchor. After the signed-URL upload, `HEAD` the object through a signed download URL and read `storage.objects.metadata->>'eTag'` for the path: confirm it equals the MD5 of the uploaded bytes and that `owner` is the uploader's uuid; retain the response headers (no bytes). If the eTag is not the plain MD5, do not proceed to finalize: record the observed format and switch to the fallback verifier before any hosted evidence is finalized.
