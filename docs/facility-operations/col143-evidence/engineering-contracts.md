## 1. Vocabulary

- **Evidence**: a row of `operation_evidence`, the immutable metadata identity of one piece of evidence for one performance receipt: classification (site, subject, authority class copied from the receipt), kind, the evidence rule it is meant to satisfy, the owned object path, declared type and size, uploader, and a state `prepared` → `uploaded` → `finalized` or `failed`. Objects live in one private bucket `operation-evidence` under the path `<facility_id>/<evidence_id>/<filename>`; the evidence id owns the path.
- **Object kinds** `document`, `photo`, `signature` carry an object. **`linked_record`** carries no object: it points at a native protected record (`facility_documents` or `employee_file_records`) under that record's own access and is finalized at preparation when the caller can read the record. **`reading`** rules are satisfied by receipt values in a later issue and stay unmet here.
- **Satisfaction**: an append-only `satisfied` event on the receipt when every applicable required evidence rule has at least `min_count` finalized evidence rows with that rule label. The receipt's original `missing_evidence` and every performance fact stay immutable; the receipt gains `evidence_status_current` and `evidence_satisfied_at`, and the occurrence moves on without a second completion click.

## 2. Schema (migration 343)

### 2.1 `operation_evidence`

| column | rule |
|---|---|
| id; organization_id; facility_id; activity_id; subject_id; authority_class | copied from the receipt's occurrence |
| receipt_id → operation_execution_receipts (performance, not superseded); task_instance_id | |
| evidence_kind | `document` / `photo` / `signature` / `linked_record` |
| rule_label text NULL | the governing evidence rule (`label`) this satisfies, whose `kind` must equal `evidence_kind`; NULL = supplementary (never counts toward satisfaction, never blocks) |
| state | `prepared` / `uploaded` / `finalized` / `failed` |
| bucket_id | constant `operation-evidence` for object kinds; NULL for linked_record |
| object_path | `<facility_id>/<id>/<filename>`; filename `^[A-Za-z0-9][A-Za-z0-9._-]{0,119}$`; NULL for linked_record |
| declared_mime, declared_size_bytes | in the bucket's allowed types (`application/pdf`, `image/jpeg`, `image/png`, `image/webp`) and ≤ 20 MiB |
| declared_sha256 text NULL | client-declared; recorded, not verified locally (`checksum_verified boolean default false`; the hosted verifier is part of the blocked acceptance) |
| object_id uuid NULL, object_etag text NULL, object_size_bytes bigint NULL, object_mime text NULL | from `storage.objects` at finalization; size and mime must equal the declared values |
| linked_table text NULL, linked_record_id uuid NULL | `facility_documents` or `employee_file_records`; readable by the caller under that table's own policies (checked by a definer helper that returns only a boolean for the caller) and belonging to the receipt's subject: an employee file record must be the receipt subject's own staff record with a category compatible with the receipt's authority class (medical only for `employee_medical`); a facility document must be at the receipt's site and the receipt subject must be the facility or an asset |
| uploaded_by → user_profiles; prepared_at; uploaded_at; finalized_at; finalized_by; failed_at; failure_reason | server-owned |
| request_key UNIQUE, request_hash | preparation idempotency |
| revision text | fresh fingerprint on every write |

CHECKs per kind and state (object kinds need bucket/path/mime/size; linked_record needs table and id and is finalized on insert; finalized object rows carry object_id/etag/size/mime; failed rows carry reason). Unique `(receipt_id, declared_sha256) WHERE state='finalized' AND declared_sha256 IS NOT NULL` so a retry with the same bytes deduplicates. Guard: token required for every write; identity columns immutable; state moves only forward (`prepared`→`uploaded`→`finalized`, `prepared|uploaded`→`failed`); no DELETE; no TRUNCATE. RLS SELECT: `haven.operation_task_readable(task_instance_id)` and (state = finalized or uploaded_by = auth.uid()). No client DML; service_role SELECT only. Audit trigger; restrictive generic-audit policy extended.

### 2.2 `operation_evidence_events`

`evidence_id` (nullable for receipt-level `satisfied`), `receipt_id`, `event_kind` (`prepared`, `uploaded`, `finalized`, `failed`, `satisfied`), actor, `expected_receipt_revision`, `request_key` UNIQUE, `request_hash`, `details`, `event_seq`, `created_at`. Insert-only under the token; RLS = receipt's task readable; audit trigger.

### 2.3 Receipt and occurrence additions

`operation_execution_receipts`: `evidence_status_current text NOT NULL DEFAULT` = the 341 `evidence_status` at insert (backfilled for existing rows; the guard sets it on insert), `evidence_satisfied_at timestamptz`. `haven.guard_operation_receipt` replaced in place: still immutable except these two columns under the token. `haven.verify_operation_work` replaced in place with its 341 body plus one change: required evidence counts as present when `evidence_status_current = 'complete'`.

Satisfaction transition (inside finalize, under the token, after the receipt and occurrence are locked): when the receipt's applicable rules are all met → `evidence_status_current='complete'`, `evidence_satisfied_at=clock_timestamp()`, `satisfied` event; if the occurrence's `execution_state='performed_missing_evidence'` for this receipt → `awaiting_verification` when the central version requires review (mirrors as 341: `signed_by` stays the recorder) else `completed` (`status='completed'`, `completed_at=clock_timestamp()`, `verified_by`/`verified_at` = the recorder as 341 does for a self-completed receipt, `sla_met` from the original `performed_at`). Nothing else on the receipt or occurrence changes; the original performer, performed-at and recorded-at are untouched (probed by column comparison).

### 2.4 Storage

`INSERT INTO storage.buckets` `operation-evidence` (private, 20 MiB, the four MIME types). `haven.operation_evidence_storage_access(p_bucket, p_name, p_write)` (definer): parses `<facility>/<evidence>/<filename>`, loads the evidence row FOR SHARE, and returns: write allowed only when `state='prepared'`, `uploaded_by = auth.uid()`, `object_path = p_name` and the receipt's task is readable by the caller; read allowed when the task is readable and (`state='finalized'` or the caller is the uploader). Policies on `storage.objects` exactly as 335: permissive read/insert for the bucket via the function, restrictive boundaries for read/insert, no client update or delete. Corporate download is a signed URL from the session client, so the same policy decides.

## 3. Commands (session; token; `haven.lock_operation_work_authority(task, governing recorder list)` before and after DML; public INVOKER wrappers to authenticated only)

Lock order for every evidence command: read the receipt without a row lock only to find its occurrence, take the work-authority lock on the occurrence first (the order 341's verification uses), then re-read the receipt `FOR NO KEY UPDATE`. Two evidence commands on one receipt therefore serialise on the occurrence row instead of deadlocking on the receipt. The storage access function checks organisation and task readability before it takes any row lock, so an other-site caller can never hold a lock on someone's evidence.

- `prepare_operation_evidence_review(p_receipt uuid, p_request_key text, p_payload jsonb)`: payload `kind`, `rule_label?`, `filename`, `mime`, `size_bytes`, `sha256?` (object kinds) or `kind='linked_record'`, `rule_label?`, `linked_table`, `linked_record_id`. Order: shape → lock (receipt FOR SHARE, its task via the work-authority lock with the governing recorder list) → replay lookup → receipt is a performance receipt, not superseded → rule_label, when given, names a governing rule whose kind matches and that is not yet met (otherwise `Evidence rule is already satisfied` / `Evidence rule does not exist for this receipt`) → declared type and size within limits → a finalized row with the same `sha256` on this receipt replays as `Evidence already finalized for these bytes` (P0001 with the existing id) → insert `prepared` (object kinds) or `finalized` (linked_record, after the readability check; satisfaction evaluated immediately) → `prepared` event → return `{ evidence, event, replayed }` (object_path included for the uploader).
- `mark_operation_evidence_uploaded_review(p_evidence, p_request_key)`: prepared → uploaded when a `storage.objects` row exists for the bucket and path owned by the caller (`owner = auth.uid()`; the uuid `owner` column exists on hosted Supabase and in the local stub, unlike the newer text `owner_id`); records object id, etag (`metadata->>'eTag'`), size (`metadata->>'size'`), mime (`metadata->>'mimetype'`); refuses when the object's size or mime differ from the declared values (`Uploaded object does not match the prepared evidence`). Idempotent.
- `finalize_operation_evidence_review(p_evidence, p_request_key, p_expected_receipt_revision, p_payload {sha256?})`: uploaded (or prepared, in which case the object check of the previous command runs first) → finalized; `p_expected_receipt_revision` must equal the receipt's current `revision` (`Receipt changed since it was read`, P0001 → 409; this is how a concurrent correction conflicts safely); `finalized` event; then satisfaction as §2.3. Idempotent by key; a second finalize with another key on a finalized row replays `already finalized`.
- `fail_operation_evidence_review(p_evidence, p_request_key, p_payload {reason})`: prepared/uploaded → failed with reason; `failed` event; the receipt stays `performed_missing_evidence` when the rule was required; a failed supplementary row never appears attached (reads of attached evidence list only finalized rows).
- Actor rule: the caller must be a recorder for the activity (governing list) with current site and subject authority, as for recording; the uploader of a prepared or uploaded row is the only one who may mark it uploaded, finalize it or fail it (`Evidence belongs to another uploader`). Other actors cannot read an in-flight row at all (RLS shows finalized rows or the caller's own), so an abandoned in-flight row is simply never attached; it blocks nothing and a fresh preparation by anyone with recorder authority proceeds.
- Replies: prepare returns `satisfaction` too (a linked record finalizes at insert and may satisfy the receipt). When Storage refuses to sign the upload URL after a successful prepare, the route returns 200 with `upload: null` and `upload_error`; the row exists in `prepared` and the same request key replays it to obtain a URL later. The list shows the caller's own failed rows (state `failed`, no path) so a retry can be reasoned about; only finalized rows are "attached".

## 4. Runtime and API

- `src/lib/operations/evidence.ts`: zod schemas (strict; filename regex; MIME enum; size ≤ 20 MiB; sha256 64-hex optional; linked kinds), `EVIDENCE_SELECT` (no object_path except for the uploader's own rows in `prepared`/`uploaded` state; the list route filters), `mapEvidenceRpcError` with the outcome classes and per-command nouns, `ATTACHED` filter helper.
- Routes: `POST /api/admin/operations/evidence` (body `receipt_id`, `request_key`, `payload`; after the RPC, for object kinds the route asks the session client for `storage.from("operation-evidence").createSignedUploadUrl(object_path)` and returns `{ evidence, upload: { path, token|signedUrl } }`; RLS on `storage.objects` decides; no service-role Storage call), `POST /api/admin/operations/evidence/[id]/uploaded`, `POST …/[id]/finalize`, `POST …/[id]/fail`, `GET /api/admin/operations/evidence?receipt_id=` (finalized rows for everyone with task access plus the caller's own in-flight rows; never `object_path` for other uploaders' unfinalized rows), `GET …/[id]/download` (only `finalized`, signed download URL from the session client, 60 s). Pattern as COL-142/144: `requireOperationsActor(OPERATIONS_VIEW_ROLES)` → strict body → session read of the receipt/evidence (404) → `actorCanAccessFacility` (404) → `revalidateOperationsActor` → RPC → mapping; replies strip `request_hash`.
- Task-list and receipts responses never carry object paths or filenames; `GET …/receipts` (COL-142) adds `evidence_status_current` and `evidence_satisfied_at`.

## 5. Verification

- Probe (rolls back; fixtures reuse the 341/342 shape plus `storage.objects` rows inserted directly to stand in for uploads, as 335's probe does): prepare for a required photo rule → prepared row with owned path, event; replay idempotent; wrong kind for the rule, unknown rule, already-met rule, disallowed MIME, oversize, bad filename refused; another site's admin and a non-recorder denied before any row; storage access function: uploader may write only its own prepared path, others cannot, nobody can write after finalization, readers see only finalized objects unless uploader; uploaded requires the object row owned by the caller with matching size and mime (mismatch refused); finalize with a stale receipt revision refused; finalize → finalized, `finalized` event, satisfaction: receipt `evidence_status_current='complete'`, occurrence `performed_missing_evidence` → `completed` (or `awaiting_verification` on a review-required activity, and then 341 verify succeeds), original performer/performed_at/recorded_at and the receipt's immutable `missing_evidence` unchanged (column comparison), no second receipt; a failed required upload leaves `performed_missing_evidence`; a failed supplementary row is absent from the attached list; retry after failure with a new prepare finalizes once; a second prepare with the same sha256 after finalization replays the existing id; wrong-site object path, unowned object, unfinalized row cannot satisfy; linked_record to a readable `facility_documents` row finalizes at once, an unreadable or other-site record refused; direct DML denied for authenticated and service_role with the forged setting; evidence and events immutable; the other site sees no evidence, event or object; receipts and task list carry no path; all earlier probes pass.
- Race script: two finalizes of the same evidence concurrently → one `finalized` event and one satisfaction; finalize racing a receipt revision change (simulated by the owner token rotating the receipt revision, standing in for an HFO-08 correction) → the finalize that loses gets the revision conflict, no satisfaction.
- Vitest: evidence library (schemas, mapping), routes (prepare with signed upload URL from the session client only, uploaded, finalize, fail, list filtering of paths, download only when finalized).
- Gates: focused suite, typecheck, lint, native replay, strict gate `--segment COL-143-HFO-EVIDENCE --ui`.
