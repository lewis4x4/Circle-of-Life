## Acceptance

1. Two assets of the same type receive distinct occurrences; concurrent runs generate one per intended subject/period: probe (two asset bindings → two rows; replay → `existing` with the same ids), race script (two generators on one period → one row, both report the same id; a retirement committed during the lock wait → no row).
2. Publishing a new configuration within the same period does not duplicate; missed periods and prior evidence survive catch-up and retirement: probe (revised and same-day-cutover configurations keep the original snapshot and converge; catch-up after retirement creates nothing; reconciliation cancels only future pending work and leaves in-progress and completed rows; cancelled and removed identities are never recreated).
3. Early, late and unknown-schedule work is never silently re-dated; later association is auditable reconciliation: probe (manual rows carry no period or deadline and a labelled queue date; association requires the current revision, is idempotent, refuses a second target, changes neither row and writes two audit rows; legacy defer and reinstate refuse managed rows).

## Boundaries kept

No binding exists for any real subject; the only bindings and managed occurrences ever created are synthetic probe fixtures that roll back. The `event` path exists in the database and the probe only (Q05 open). Completion receipts are COL-142, evidence transport COL-143, reminder delivery HFO-15; a service job that escalates or marks managed occurrences missed will need its own approved command because the identity guard refuses service updates outside the commands (no live job writes instances today: the escalation scanner is closed). A binding may name a shift, and the generation command honours shifted evaluator items, but no version-1 rule shape carries a shift, so the scheduler sends none and a shifted binding is reported as `no_binding` until a shifted rule shape exists (known limit, recorded in `OWNER-DECISIONS.md` 3c). Six engineering policies are listed for confirmation there. Design choices the SQL review noted and this segment keeps: a binding retired by an administrator does not cancel its future pending work by itself (the explicit cancel command does; the service reconciliation covers only subjects that stopped being current); `occurrence_revision` is a fresh fingerprint on every write; manual work on an employee is classified `employee_personnel` (no manual `employee_medical` recording); request keys are unique across the whole table, not per organisation; retiring a binding with a future end frees the open slot immediately and generation still converges on the subject identity.
