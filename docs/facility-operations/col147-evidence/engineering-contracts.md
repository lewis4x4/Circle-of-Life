**What this segment is.** The shared mechanism by which a *final* domain record (a drill log, a generator observation, a weight, a signed document, a training certificate) can satisfy exactly the occurrence it was meant for, once, and by which its later correction or void appends history instead of erasing it. **What it is not.** No domain adapter is registered, no reader is written for any real table, no source is declared final, no provider behaviour is assumed and no policy, owner or date is invented. Those are COL-154 through COL-159. The allowlist in 346 is empty; the probe registers a synthetic adapter over a synthetic table and rolls back.

## 1. Vocabulary

- **Source adapter**: an allowlist entry (`operation_source_adapters`) naming a `source_key`, the typed subject kind the source describes, and the **reader** (`haven.<function>(text) RETURNS jsonb`) that returns the live state of one source record. Registration happens only by migration in a later domain segment; 346 registers none and grants no role the right to register one.
- **Source rule**: an allowlist pair (`operation_source_rules`) of `source_key` and `activity_id`. A reader may name only an allowlisted activity for its source; anything else is refused as `activity_not_allowlisted`.
- **Reader snapshot**: the reader's answer for a record id, read live by the command *at delivery time* (never trusted from the caller): `exists`, `version`, `finality` (`draft` | `final` | `voided`), `facility_id`, `activity_id`, `subject { kind, id }`, `recorded_by`, `recorded_at`, and `statement` in the exact 341 record-payload shape (`performed_at`, `performer`, `entry_kind`, `entry_reason`, `outcome`, `values`, `note`, `issue`). The reader decides the mapping from domain columns to that shape; the shared mechanism decides nothing about domain finality.
- **Delivery** (`operation_source_events`): one immutable ledger row per (organisation, source_key, source_record_id, source_record_version, event_kind) with the request key and fingerprint of the delivery, who delivered it (a session actor or the service), the snapshot as read, the matching outcome, and a forward-only reconciliation state. `event_kind` is `final` (this version is final and should satisfy) or `voided` (this record is void and should invalidate).
- **Matching predicate**: activity (from the snapshot, allowlisted), site (`facility_id` claimed by the deliverer *and* returned by the reader; both must agree), subject (the snapshot's typed native id resolved to the one `operation_activity_subjects` row for that site; the adapter's subject kind must equal the activity's), period (the occurrence whose `period_start_date … period_end_date` contains the performed instant's local date in the occurrence's own snapshot timezone) and rule (the occurrence's pinned `requirement_version_id` / `facility_requirement_id`, against which the statement is validated exactly as a human recording is). Only managed `scheduled` and `event` occurrences that are not cancelled or removed are candidates.
- **Satisfaction**: a performance receipt written by the mechanism whose `recorder_id` is the source's `recorded_by`, whose `recorded_at` is the server clock at delivery, whose performed instant, performer, entry kind and values come from the statement, and which carries `source_event_id`, `source_key`, `source_record_id`, `source_record_version`. Everything else about the occurrence projection is the 341/344 behaviour (state, status, `effective_receipt_id`, `performed_at`, `sla_met`, audit).
- **Invalidation**: a `voided` delivery for a source whose receipt is the effective performance receipt writes a 344 reversal (`correction_reason` = the void), supersedes that receipt and its review, returns the occurrence to `pending` or `missed` by its deadline, and leaves the delivery in `invalidated` with `attention = true`. Nothing is deleted; the reversed chain stays readable history.
- **Pending reconciliation**: a delivery in `unmatched`, `ambiguous`, `conflict` or `invalidated` (and a `refused` delivery whose reason is a recorder-authority gap) carries `attention = true` and is visible to site administrators under current authority until a reconcile command resolves it (`retry`, `select` an explicit candidate, or `dismiss` with a reason). Reconciliation never satisfies an occurrence the predicate would not have matched.

## 2. Schema (migration 346)

### 2.1 `operation_source_adapters`

| column | rule |
|---|---|
| organization_id uuid → organizations | |
| source_key text | `^[a-z][a-z0-9-]{0,63}$`; PK with organization |
| subject_kind text | `facility` / `resident` / `employee` / `asset`; the authority class follows (`facility`, `resident`, `employee_personnel`, `asset`); no adapter may write `employee_medical` |
| reader_function text | `^[a-z][a-z0-9_]{0,62}$`; must exist as `haven.<name>(text) RETURNS jsonb` at registration and at every delivery |
| status text | `registered` / `retired`; forward-only |
| registered_at, retired_at, note | |

Guard trigger: insert and update only when `auth.uid() IS NULL` **and** the session is not the service identity (`auth.role()` is not `service_role`), i.e. only a migration or the owner; a retired adapter cannot be re-registered; the reader must exist with that signature. All DML privileges revoked from every role; `SELECT` to `authenticated` within the organisation.

### 2.2 `operation_source_rules`

`(organization_id, source_key) → adapters`, `(organization_id, activity_id) → activities`, `status` `registered`/`retired`, same guard and grants. Unique `(organization_id, source_key, activity_id)`.

### 2.3 `operation_source_events` (the ledger)

| column | rule |
|---|---|
| id uuid | |
| organization_id, facility_id | facility claimed by the deliverer; must be the reader's facility |
| source_key, source_record_id (`^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`), source_record_version (`^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`) | |
| event_kind text | `final` / `voided` |
| delivery_kind text | `session` / `service` |
| delivered_by uuid → user_profiles | NOT NULL for `session`, NULL for `service` |
| delivered_at timestamptz | server clock |
| request_key text UNIQUE, request_hash text | 341 key regex; hash over organisation, deliverer, source identity and event kind |
| activity_id, subject_id, authority_class | resolved from the snapshot when it validated; NULL when refused earlier |
| task_instance_id uuid → operation_task_instances | the matched (or conflicting) occurrence |
| receipt_id uuid → operation_execution_receipts | the receipt this delivery wrote (performance, correction or reversal) |
| state text | `satisfied` / `corrected` / `invalidated` / `unmatched` / `ambiguous` / `conflict` / `refused` / `dismissed` |
| attention boolean | pending reconciliation |
| reason text | machine reason (`reader_missing`, `reader_failed`, `adapter_retired`, `record_missing`, `facility_mismatch`, `source_version_changed`, `source_not_final`, `source_voided`, `source_not_voided`, `activity_not_allowlisted`, `subject_kind_mismatch`, `subject_not_enrolled`, `subject_not_current`, `recorder_unknown`, `recorder_not_current`, `recorder_not_authorized`, `statement_invalid`, `no_candidate`, `several_candidates`, `already_recorded`, `nothing_to_invalidate`, `source_not_effective`, `occurrence_cancelled`); the site check comes first so another site learns nothing beyond the mismatch |
| detail text | the human-readable refusal wording (a 341/344 statement message when `statement_invalid`) |
| candidates jsonb | occurrence ids the predicate matched (for `ambiguous`) |
| snapshot jsonb | the reader's answer as read at delivery, set once and immutable; kept in full only when a subject row was resolved (the row is then readable only under that subject's authority), otherwise redacted to identity and finality (`exists`, `version`, `finality`, `facility_id`, `activity_id`, `subject.kind`, `recorded_at`, `redacted`), and to `{redacted}` alone for a site mismatch |
| reconciled_by, reconciled_at | last reconcile |
| revision text | fresh fingerprint on every write; reconcile requires the expected one |

Partial unique index on `(organization_id, source_key, source_record_id, source_record_version, event_kind) WHERE state <> 'refused'`: one **live** delivery per version and kind; a second delivery of the same version and kind, under any request key, converges on that live row (`replayed: true`) and is returned to a session only when that session may read the row (otherwise `Operation unavailable`, so another site or an actor without the subject's authority learns nothing). A refused delivery is history that never blocks a later delivery: the next delivery of the same version runs in full, and an earlier refused row that still asked for attention is marked superseded. Guard: insert/update only under the source token; `state` moves only from a pending state (`unmatched`, `ambiguous`, `conflict`, `refused` with attention) to `satisfied` / `corrected` / `dismissed` / `refused`, and from `invalidated` only to `dismissed`; `attention` moves only `true → false`; identity, snapshot (once set), delivered_* and request_* immutable; a resolved `activity_id`, `subject_id` and `authority_class` are never dropped by a later refusal (whatever was stored under that authority stays under it); a settled row changes only its reconcile stamp; no DELETE; no TRUNCATE. Audit trigger; hidden from the generic audit read (the ledger is the readable history).

### 2.4 `operation_source_event_attempts`

Immutable history of every reconcile: `event_id`, `seq`, `request_key UNIQUE`, `request_hash`, `actor_id`, `actor_role`, `at`, `action` (`retry` / `select` / `dismiss`), `reason`, `from_state`, `to_state`, `outcome jsonb` (state, reason, detail, attention, occurrence, receipt, the chosen occurrence and the snapshot the retry read, redacted by the same rule as the event). Insert only under the token; no update/delete; audit trigger; readable when the event is.

### 2.5 `operation_execution_receipts` additions

`source_event_id uuid → operation_source_events`, `source_key text`, `source_record_id text`, `source_record_version text`: all NULL (a human recording, correction, reversal or review) or all NOT NULL (written by this mechanism). Index on `(organization_id, source_key, source_record_id) WHERE source_event_id IS NOT NULL`, and a **partial unique index** on the same columns `WHERE receipt_kind='performance' AND superseded_by_receipt_id IS NULL AND source_event_id IS NOT NULL`: one source record is the effective receipt of at most one occurrence at a time. The 344 guard body is kept; the columns are immutable like every other receipt column.

### 2.6 Tokens and guards

A second transaction-local setting `haven.operation_source_command` compared with the same owner-secret token (`haven.operation_source_approved()`). It marks that the writes in flight belong to the source commands. The 341 body of `haven.guard_operation_current_authority` is replaced verbatim with one carve-out beside 340's cancellation carve-out: a service-identity `UPDATE` of a managed `scheduled`/`event` row that leaves `subject_id`, `authority_class`, `deleted_at`, `completion_evidence_paths` and `created_by` untouched, and never sets `completed` without an effective receipt, is accepted when both tokens are set. (The 340/341 identity guard already requires the occurrence token for every managed-row change, so no other path widens.) `operation_audit_log.event_type` gains `source_linked`, `source_pending`, `source_invalidated`.

## 3. Commands

Order in every command: shape → adapter allowlist → **domain access** (a session deliverer must currently hold the site and, for a protected subject kind, that domain's recording scope, before the source is read at all; the service locks the site) → per-record advisory lock → replay by request key (same content → the stored reply, `replayed: true`, only if the actor may read it; different → `This request was already saved with different content`) → convergence on the live row (readable only) → live snapshot → snapshot validation → ledger insert (a unique violation on the live key means another delivery of this version committed meanwhile, so re-read and return it as `replayed: true` when readable) → candidate lock → authority lock → statement → write under both tokens → re-lock → reply.

### 3.1 `deliver_operation_source_event_review(p_request_key text, p_payload jsonb)` (session) and `deliver_operation_source_event_service(p_request_key text, p_payload jsonb)` (service)

Payload: `{ source_key, source_record_id, source_record_version, event_kind, facility_id, organization_id? }`. The session wrapper refuses when `auth.uid()` is NULL, takes the organisation from the claims and refuses a payload organisation that differs; the service wrapper refuses when `auth.uid()` is not NULL and requires `organization_id`.

Snapshot validation (each failure is a **recorded** `refused` row, never an exception, so the ledger keeps the attempt): the reader must exist and return an object (`reader_missing`, `reader_failed`, both with attention because they are transient); `exists=false` → `record_missing`; `facility_id` must equal the claimed site and belong to the organisation (`facility_mismatch`, checked before anything else about the record is reported); `version <> source_record_version` → `source_version_changed` (the newer version's own delivery is the one that counts); `event_kind='final'` requires `finality='final'` (`draft` → `source_not_final`, `voided` → `source_voided`); `event_kind='voided'` requires `finality='voided'` (`source_not_voided`); `activity_id` must be allowlisted for the source (`activity_not_allowlisted`); the activity's subject kind must equal the adapter's (`subject_kind_mismatch`); the resolved subject must still be current at the site (`subject_not_current`, pending, stored without the subject and with a redacted snapshot so the site can see and dismiss it; checked before the session's subject accessibility); `recorded_by` must be an active profile of the organisation (`recorder_unknown`, `recorder_not_current` with attention). Shape errors of the payload itself (missing keys, bad regex) raise 22023 before any row is written, exactly as 341 does for a malformed record payload.

Subject resolution: `facility` kind resolves (or creates, as the 340 generator does) the site's one facility subject; `resident`, `employee` and `asset` must already have their `operation_activity_subjects` row for that site (a 340 binding created it), otherwise `unmatched` with `subject_not_enrolled` and attention.

Authority: **session** delivery locks the delivering actor's current authority on the matched occurrence with the 341 work-authority lock (NULL role list: current site, subject and session; the recorder-list gate is applied to the *source author*, not to the deliverer), and, when nothing matched, requires current site access for the claimed site. **Service** delivery locks the facility, the subject's native row and the candidate occurrences, exactly as the 340 generator does, and asserts nothing about a person's authority except the source author's recorder role.

`final` on one candidate: when this record is already the effective receipt of *another* occurrence (an earlier version covered another period) and the candidate is unrecorded, the new version is first validated in full against the candidate (author known, active and on the recorder list; statement valid) without writing anything; only then is the earlier receipt invalidated (a 344 reversal whose reason names both versions and the move) and the candidate satisfied as a fresh chain, so a record is never the effective receipt of two occurrences and an invalid later version strips nothing; otherwise no effective performance receipt → **satisfy**; effective receipt from the *same source record* (any earlier version) → **correct** (a 344 correction whose `correction_reason` names the source and both versions; evidence carries across the chain; a bound review is superseded and the occurrence awaits review again when the rule requires it); effective receipt from a human recording or another source → `conflict` with attention (the delivery names that occurrence and receipt; nothing is overwritten). Zero candidates → `unmatched`; several → `ambiguous` with the candidate ids. A cancelled or removed candidate is not a candidate. A candidate in `execution_state` other than `none` without an effective receipt cannot occur (344 keeps `none` after a reversal); the command still treats it as `conflict` rather than assuming.

The statement is validated by the shared 344 helper `haven.operation_work_statement` with the reference instant = the **source's own `recorded_at`** (so a source entered more than fifteen minutes after the work must state `late` with a reason in its own record, and a performed time after the source's recording is refused), the default performed instant = the source's `recorded_at`, and no chain (a fresh recording) or the existing chain (a correction). A statement failure is a recorded `refused` row with `statement_invalid` and the 341/344 wording in `detail`. The governing recorder list (`fr.local_allowed_recorder_roles` else `v.allowed_recorder_roles`) is applied to the source author's current `app_role`; a mismatch is `refused` / `recorder_not_authorized` **with attention**, because a domain record by a person outside the published list is a policy question for the site, not something to hide.

`voided`: matched by **source identity**, not by period (the void's author must be an active person of the organisation, else `recorder_not_current` with attention): the effective performance receipt anywhere in the organisation carrying this `source_key` and `source_record_id` → **invalidate** (344 reversal semantics under the source token; `attention = true`); such a receipt exists only superseded (already corrected by a person or reversed) → `refused` / `source_not_effective` with attention (history retained; the person's restatement is not erased by the void); none → `refused` / `nothing_to_invalidate` without attention.

Reply: `{ event, occurrence | null, receipt | null, candidates, replayed }` where `event` is the ledger row (`snapshot` included; RLS decides who can read it back), `occurrence` the 341 five-key projection (`id`, `status`, `execution_state`, `occurrence_revision`, `performed_at`), `receipt` the receipt written by this delivery. A `reader_failed` refusal keeps the reader's own error text (bounded to 2000 characters) in `detail`: readers are owner-written migration code and their wording is the diagnostic the site needs; a reader must not raise with protected data.

### 3.2 `reconcile_operation_source_event_review(p_event uuid, p_request_key text, p_expected_revision text, p_payload jsonb)` (session)

Payload `{ action: 'retry' | 'select' | 'dismiss', occurrence_id?, reason? }`. Requires the actor to hold the COL-133 broad operations mutation scope at the event's site (owner, org_admin, facility_admin, manager, admin_assistant, coordinator) with a current site grant, and, for `retry`/`select`, the 341 work-authority lock on the chosen occurrence. Lock order is the delivery's: the per-record advisory lock, then the ledger row, so a retry racing a re-delivery of the same version waits rather than deadlocking. `p_expected_revision` must equal the event's `revision` (else `Event changed since it was read`, P0001, DETAIL `current_event_revision=<rev>`). Replay by request key through `operation_source_event_attempts`. Only pending states may be reconciled; `invalidated` accepts `dismiss` only.

`retry`: re-reads the live snapshot (same validation; a changed version refuses, since that version's delivery must arrive on its own; a reader that cannot answer raises `Source reader unavailable` and leaves the row and its attempts untouched) and re-runs the predicate and satisfaction exactly as 3.1; the delivery's own snapshot is never overwritten, the retry's snapshot goes into the attempt. `select` requires `occurrence_id` to be among the predicate's current candidates (same activity, site, subject and a period containing the performed instant); it never widens the predicate, it only resolves `ambiguous`. `dismiss` requires `reason` (1–2000), sets `dismissed`, `attention=false`, and writes nothing to any occurrence. Every attempt is one immutable row; the event's `revision` changes on every write.

## 4. Runtime and API

- `src/lib/operations/source-links.ts`: `deliverSourceEventBodySchema`, `reconcileSourceEventBodySchema`, `SOURCE_EVENT_SELECT`, `SOURCE_EVENT_STATES`, `SOURCE_EVENT_REASONS`, `isSourceDeliveryOutcome`, mapping through `mapReceiptRpcError` with the new commands `deliver` and `reconcile`, trusted fragments only for 346 RAISE wordings (`not allowlisted`, `not a candidate`, `applies to select only`, `does not match the caller`; the rest already match `must be`, `is required`, `requires`, `not editable`, `changed since`) so Postgres constraint names stay hidden; `Source delivery is settled` and a moved event revision are conflicts, the latter carrying `current_event_revision`.
- Routes: `POST /api/admin/operations/source-events` (session delivery: `requireOperationsActor(RECEIPT_COMMAND_ROLES)` → strict body → the claimed site must be accessible (404 otherwise) → `revalidateOperationsActor` → RPC → mapping); `GET /api/admin/operations/source-events?facility_id=&attention=true|false&state=` (the pending-reconciliation queue by default, any state when named, read through the session; provider-capped reads paged to exhaustion with `readAllOperationRows`; ordered by `delivered_at`, `id`; the exact total is the number of rows read, never a page length); `POST /api/admin/operations/source-events/[id]/reconcile`. Responses strip `request_hash`.
- No UI. No scheduler or Edge Function calls any of this; the service wrapper exists for the later domain outbox drains and is executable only by `service_role`.

## 5. Verification

- Probe (rolls back; synthetic adapter `probe-log` over a synthetic table with `finality`, `version`, `facility`, `subject`, `recorded_by`, `performed_at`): a final matching record satisfies exactly its occurrence once (receipt carries the source columns, recorder is the source author, occurrence completed, audit `source_linked`); replay by the same key and a second delivery of the same version under another key both return the one row; a draft, a voided record, a stale version, a missing record, a wrong site, a wrong subject, a non-allowlisted activity, a period outside every occurrence, a cancelled occurrence and an author outside the recorder list each leave a recorded refusal or pending row and write no receipt; a second matching occurrence (two shifts) is `ambiguous` and `select` resolves it while `select` of a non-candidate is refused; a human recording on the target makes the delivery `conflict` without overwriting; a corrected version supersedes the earlier source receipt with the chain, reason and reopened review; a void reverses the source receipt, keeps every prior receipt verbatim, returns the occurrence to `pending`/`missed`, and leaves an `invalidated` row that only `dismiss` can close; a void after a human correction is `source_not_effective` with attention; a void of a never-linked record is `nothing_to_invalidate`; reconcile with a stale revision conflicts; `dismiss` needs a reason and touches no occurrence; the service wrapper refuses a session and the session wrapper refuses the service; the other site sees no event; direct DML on adapters, rules, events, attempts and receipt source columns is refused with and without the forged setting; DELETE and TRUNCATE refused; a forced audit failure leaves ledger, receipts and occurrence untouched; the 341, 343, 344 and 345 probes pass unchanged.
- Race script (observed lock waits, eight orderings): two deliveries of one version under different keys → one receipt, the second converges; a retry of a refused-with-attention row racing a re-delivery of the same version → the second waits on the advisory lock and converges, no deadlock; a delivery racing a human recording on the same occurrence, both orders → whichever lands second is the conflict (`Work is already recorded` for the person, `conflict` pending for the source); a void racing a human correction of the source receipt, both orders → the second is refused naming the winner; versions 1 and 2 racing → either order yields one effective receipt at the live version and the stale one is `source_version_changed`.
- Vitest: schemas, mapping, three routes (site guard before the command, zod refusal, request key forwarding, RPC error classes, exhaustive paging with exact totals, partial-read failure explicit).
- Gates: focused suite, typecheck, lint, native replay on the retained scratch cluster, strict `npm run segment:gates -- --segment COL-147-HFO-SOURCE-ADAPTERS` (no `--ui`: no UI changed).

## 6. Boundaries kept

No adapter, reader, rule or source registered; no drill, generator, resident, employee, census, dietary or provider connection (COL-154–159). No finality inferred from a row's existence; every delivery re-reads the source live. No invention of who may reconcile beyond the existing COL-133 broad operations scope. No scheduler, reminder, notification or external transmission. Engineering policies to list in `OWNER-DECISIONS.md` (3j): (i) the source author is the receipt's recorder and must be an active person currently holding a role on the governing recorder list, else the delivery is refused with attention; (vii) a session deliverer needs current site access and, for a protected subject kind, that domain's recording scope, and only sees replies and ledger rows they could read; refusals for unresolved subjects keep no statement, author or native id; (ii) the late rule is anchored on the source's own recording instant; (iii) a corrected source version supersedes its earlier receipt as a 344 correction and reopens review when the rule requires it; (iv) a void reverses only a receipt this source wrote and that is still effective, and always leaves an attention row; (v) a delivery that finds a human receipt on its occurrence conflicts rather than overwriting; (vi) `select` resolves ambiguity only among predicate candidates; period is never overridden by reconciliation. Source only; hosted, provider, staff and operating acceptance are not established.
