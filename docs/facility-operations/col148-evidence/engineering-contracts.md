## 1. What is built

One site work surface for administrators and assistants at `/admin/operations/work`, with three views in the URL (`?view=today|upcoming|history`, plus `facility_id` and `mine=1`), reachable from both role entry points: a "Site work" item in the admin shell's Command group and in the `admin_assistant` `visibleItemKeys` allowlist, and a link from the existing `/admin/operations` page. Roles: `OPERATIONS_VIEW_ROLES`; every write stays governed by the database commands.

- **Today**: managed occurrences at the site whose deadline (grace end when set, else due) falls on or before the end of the facility's today and that are not finished (`pending`, `in_progress`, `missed`, `deferred`, and `in_progress` with `execution_state` `performed_missing_evidence` or `awaiting_verification`), grouped as *Due today*, *Outstanding from earlier* (never hidden, however old) and *Unknown schedule* (occurrences with no deadline or `due_judgment` unknown, shown with "Record unscheduled work"), plus unfinished legacy (unmanaged) tasks assigned on or before the facility’s today, without an age lower bound or application row cap, in a *Legacy tasks* group that keeps the legacy actions. Unassigned duties are shown; `mine=1` only narrows to the actor's role being in the governing recorder list, never hiding unassigned work by default.
- **Upcoming**: managed occurrences with a deadline after today through fourteen days ahead, read-only except "Report an issue".
- **History**: the site's finished or reversed occurrences newest first, cursor-paginated (fifty per page, keyset on `(due_at desc nulls last, id desc)` (the database due instant, not the grace-coalesced display deadline)), with the complete count from a separate server count (never the page length), each row expandable to its receipt chain (recordings, corrections, reversals, reviews), attached evidence and issues, and offering *Correct* and *Reverse* (COL-145) with a reason.

## 2. Server read (`src/lib/operations/workspace.ts`, `GET /api/admin/operations/workspace`)

Query `facility_id` (uuid, required), `view`, `cursor?`, `mine?`. Pattern as the existing list routes: `requireOperationsActor(OPERATIONS_VIEW_ROLES)` → `actorCanAccessFacility` (404) → session-client reads only (RLS governs every row; no service role). Composition, all on the server: (1) occurrences from `operation_task_instances` with `OCCURRENCE_SELECT` (managed rows) for the view's window; (2) the governing rules resolved per distinct `(requirement_version_id, facility_requirement_id)`: required inputs, required evidence (with `when`), recorder roles, `review_required`, coalescing local over central exactly as 341 does; (3) the effective receipt per occurrence (`effective_receipt_id` → `RECEIPT_SELECT` plus `evidence_status_current`, `evidence_satisfied_at`, `missing_evidence`, `revision`); (4) open issue counts per occurrence (COL-144 read); (5) for Today, unfinished legacy tasks through the existing list response helper, bounded only above by the facility-local date; bypass `parseOperationTaskFilters` because its date-only parsing can shift days with the host timezone. Reply `{ view, facility_id, facility_timezone, generated_at, groups: { due_today, outstanding, unknown_schedule, legacy } | { upcoming } | { history, next_cursor, total }, actor: { id, name, role } }` with each managed item `{ occurrence (id, activity name, subject label, deadline, grace, status, execution_state, occurrence_revision, schedule_status), rules { inputs, evidence, recorder_roles, review_required, can_record: boolean (role in list) }, receipt | null, open_issues, evidence_summary { required_rules: number | null, satisfied } | null }`. `required_rules` is null for an evidence-requiring receipt and zero for `not_required`; without a receipt it counts prospective performed-outcome rules, not attachments or `min_count` totals. A correction’s immutable `missing_evidence` snapshot omits carried evidence, so it cannot establish the full rule count. `satisfied` uses current aggregate status (`complete` or `not_required`) only. A missing pinned effective receipt yields null summary and `partial: ["receipts"]`, never a prospective replacement. Missing pinned versions or local requirements yield null rules and `partial: ["rules"]`; an unreadable local requirement must not fall back to central rules. History cursors require strict timestamp syntax and preserve microseconds in both equality and comparison predicates. Partial or failed sub-reads never degrade to an empty success: the reply carries `partial: [ 'rules' | 'receipts' | 'issues' | 'legacy' | 'total' ]` and the page shows the failed part as failed. Loading, empty, partial and error are distinct states.

All unbounded lists (Today, Upcoming, legacy, reversal receipts and issues) use stable ordering with an id tiebreak and range reads of up to 500, advancing by actual returned rows until an empty page. A short page is not an end marker, so a provider cap below 500 cannot silently truncate the result. Dependent id filters (rules, receipts, issues and legacy assignees) are batched at 100 ids and paged the same way. Any later-page failure discards that incomplete read and returns primary failure or the existing sub-read partial marker. History reads disjoint sources: finished/receipted occurrences, then deduplicated reversal-id batches excluding those base rows. Each source applies the same cursor/order/51-row fetch and a separate exact count without the cursor; candidates merge using whole-second UTC plus six-digit microseconds and id, then take 51. Counts sum across disjoint sources. This preserves PostgreSQL timestamp precision and keeps reversal filters bounded without an age or membership cap. The occurrence receipt-chain, per-receipt evidence and issue-list GET routes use the same shared `readAllOperationRows` helper (`src/lib/operations/read-all.ts`), with recorded/prepared/reported time and unique id ordering. They return a complete list or 503 on any page failure; evidence visibility/redaction, session authority and all POST command paths stay governed by their existing contracts. The separate History count remains site-wide when `mine` is selected; filtered pages can be empty with a non-null next cursor and must retain the Next control.

## 3. Client (`src/app/(admin)/admin/operations/work/page.tsx` and `_components/`)

- **One-action Complete** on a managed row whose rules require no inputs and no evidence for a performed outcome: one button, no note, no reviewer, no modal; it posts `record` with `{ outcome: 'performed' }` and a fresh `request_key` through the COL-146 machine (`usePendingSave`), and the row updates in place from the reply (status, execution state, receipt) without a list reload. Legacy rows keep the legacy complete route. When the rules require inputs, the row expands inline to a form of exactly those inputs (typed by the rule: number with unit/min/max, text, boolean, choice, datetime through `QuietDatePicker` with empty staying empty); when an evidence rule applies to the chosen outcome, the evidence step appears inline after the receipt is saved (`performed_missing_evidence`): pick a file, the client computes MD5 with `md5OfBlob`, prepare → PUT to the signed URL → uploaded → finalize with the receipt revision, each step's state visible (COL-146 notice `uploading`), and a failed checksum shows the durable failure with "Try another file". Nothing evidence-related appears when no rule applies.
- **Late, on behalf, failed, not performed** are behind one "More options" disclosure on the row (performed time, performer, reason, outcome), never in the default path.
- **Report an issue** on every managed row: summary, kind, severity → `POST /api/admin/operations/issues` with the occurrence; changes no occurrence state; the row's open issue count updates in place.
- **Inline receipt**: after any save the row shows "Recorded by {person} at {facility local time}", the outcome and the evidence status from the server reply, never from client state; a replay (`replayed: true`) shows the same receipt with "already saved".
- **Current person** on the page header and on every recording surface (the COL-146 notice's current person), with the existing sign-out as the user-switch path; the pending-save hook drops state on actor change.
- **Preserve position**: view and filters live in the URL search params; rows update in place; the acting control keeps focus after complete, cancel and retry (focus is returned to the row's primary button by id); no full-list refetch after an action (a background refresh merges by id and never scrolls); expanded rows stay expanded across an action.
- **Keyboard, touch, mobile**: every action is a button; disclosures use `aria-expanded`; live region announces save states; targets at least 44 px; single-column layout under the `md` breakpoint; the list is a semantic list, not a virtualised table (T2List's DataTable virtualises above 100 rows and would break scroll and focus retention).
- **Design**: PageShell supplies TopBar and AuditFooter; native labeled single-site and fixed-view controls replace FilterBar’s multi-site/date-range controls so unsupported filters are not implied. Other primitives imported directly (`PageShell`, `PageHeader`, `FilterBar`, `Panel`, `Note`, `SeverityChip`, `AuditFooter`) as the rounding and vitals pages do; semantic Tailwind token classes only; the COL-146 `SaveStateNotice`.
- **Navigation**: `AdminShell` Command group gains "Site work" → `/admin/operations/work` (key `site-work`); `admin_assistant` allowlist gains `site-work`; the legacy `/admin/operations` page gains a link to it.

## 5. Boundaries kept

No migration; no new command; no corporate history or counts (COL-149, COL-150); no export (COL-151); no reminders (COL-152); no offline drafts (Q25). The workspace never infers ownership from a role name (Q02), never hides unassigned or overdue work, never marks anything complete that the server did not, and never carries object paths. Engineering policies to list in `OWNER-DECISIONS.md` (3i): (i) Upcoming spans fourteen days; (ii) History pages by fifty with keyset pagination; (iii) legacy tasks keep their legacy actions in a separate group until their rules are approved; (iv) one-action complete applies only when the published rules require nothing else for a performed outcome. Source only; staff and device acceptance are COL-140/COL-21 matters.

**Evidence count clarification:** `missing_evidence` is the immutable unmet-rule snapshot at recording/correction. Corrections can carry evidence, so that snapshot cannot establish the full required count. `required_rules` is null for an evidence-requiring receipt, zero for `not_required`, and the prospective applicable-rule count before a receipt. `satisfied` remains the authoritative aggregate status; never infer file counts.
