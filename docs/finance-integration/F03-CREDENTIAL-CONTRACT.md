# F03 protected sandbox credential lifecycle — bounded 342 contract

This schema stages declared connections and worker-observed credentials. It does not execute OAuth/QuickBooks HTTP, provision an issuer, prove Vault encryption, enable financial dispatch, verify accounting classification, or approve business release. Production seed, resume, identity read, start and install are disabled. All existing 339/340 financial dispatch blockers remain.

## Identity and locks

A physical grant has one organization owner and is globally unique by provider (`qbo`), environment, expected company reference and **stable OAuth client identity SHA256**. A second organization receives a generic unavailable response and no other organization metadata. The whole app configuration hash is separate. Two entities using the same canonical grant serialize refresh together; distinct clients maintain separate histories. An immutable connection generation records each entity binding and explicit reconnect, with its predecessor. Credential revisions advance independently; routine refresh does not change the accounting connection generation or 339 controls.

Every mutation takes the organization advisory lock, then all organization controls ordered by entity UUID, then all organization lineages ordered by UUID, then attempt/candidate/registry rows. This deliberately overserializes sandbox operations. Registry changes obtain the organization lock before creating missing control rows. No refresh worker changes controls or 340 batches; human binding, stop, reconnect and worker changes use existing 339 control commands and 340 invalidation. Authority is rechecked after waits and before successful protected delivery/activation. No database transaction spans HTTP.

## Public invoker RPCs

All IDs are UUIDs. All returned revisions/epochs are decimal strings.

| RPC | Caller and contract |
| --- | --- |
| `finance_credential_control(p_request_id,p_entity,p_action,p_data)` | Current owner/org admin with current managed session. Metadata only. Exact request replay returns immutable receipt; changed content conflicts. Actions below. |
| `seed_finance_credential_candidate(p_id,p_entity,p_lineage,p_connection_epoch,p_input_revision,p_response)` | Current manager; explicitly resumed sandbox connection only, initial credential or explicit newer reconnect epoch, expected epoch/revision CAS, no unresolved attempt. Ready credentials cannot be replaced through seeding. Raw string goes only to a new immutable Vault secret and protected candidate reference. No token is returned. |
| `finance_credential_status(p_entity)` | Current manager; declared lineage/binding, revision, fenced/unknown state and candidate metadata only. No raw responses, Vault IDs, tokens or proofs. |
| `read_finance_credential_identity(p_id,p_candidate)` | Live assigned worker, purpose `finance_identity`. Retryable sixty-second verification lease returns **access token only**, fixed sandbox accounting host, expected company/client and GET method; never refresh token. Current connection and every bound entity/control must remain live and unstopped. Same lease can be replayed while current; a new lease can be claimed after expiry. Expired/invalid access returns reconnect-required. Trusted late candidates, old connection epochs and candidates fenced by stop/worker/connection changes cannot release access. |
| `observe_finance_credential_identity(p_id,p_candidate,p_company,p_client_sha256,p_host,p_evidence_sha256)` | Live assigned `finance_identity` worker with a current verification lease. Exact expected company/client and fixed sandbox host required. Immutable SHA-linked observation remains `worker_observed_unverified`. No raw HTTP response is accepted here. |
| `claim_finance_refresh(p_id,p_lineage)` | Live assigned worker, `finance_refresh`. No secrets. One lineage-wide attempt. Unstarted expired lease can be reclaimed; human fencing also releases a never-started claim explicitly because no refresh credential was disclosed. Started/unknown attempts block automatic reuse. |
| `start_finance_refresh(p_id)` | Same current worker/epoch, live claim, unchanged controls/connection/input revision, current observed identity. First success only returns normalized current access/refresh pair and one completion proof, with `Cache-Control: no-store` and `Pragma: no-cache`. Only proof SHA persists. Retry cannot recover credential/proof; it exposes unknown outcome, or known installed receipt if completed. |
| `capture_finance_refresh_candidate(p_id,p_candidate,p_proof,p_response)` | Original live worker, `finance_capture`, exact previously started attempt/proof. Atomically creates a new immutable Vault secret and candidate. Same candidate+byte-identical input replay is retained; differing body or a second candidate for an attempt conflicts. |
| `preserve_finance_refresh_candidate(p_id,p_candidate,p_proof,p_response)` | Actual service role with current service claim, only for exact existing started attempt/proof. Privileged completion trust; may append a late candidate after worker expiry/revocation. No read or activation capability is granted. Its candidates are always quarantined. |
| `install_finance_credential_candidate(p_id)` | Live assigned `finance_install` worker. Separately validates protected response shape and expiry, requires current observed identity, then CAS installs one revision. Attempt candidates also require original worker/epoch, live lease, current attempt/control context and candidate-pending state. Stale/late/unknown candidates remain immutable and quarantined. |

Control metadata:

- `bind`: exact provider, environment, company_reference, client_identity_sha256, app_config_sha256 and nullable expected_connection_id. Creates an immutable generation and stops/fences affected old/new lineages. It cannot silently change an existing lineage's app configuration.
- `stop`: lineage_id, expected_fence_epoch, stopped boolean. Stops or resumes all current bindings sharing that lineage, preserving history. Resume is sandbox only.
- `reconnect`: lineage_id, expected_fence_epoch, app_config_sha256. Advances connection epoch and regenerates only that same client/grant's entity bindings; stops the lineage. A previously started unknown attempt remains attached and blocks reseeding/refresh. Clearing this distributed unknown requires a future separately reviewed recovery policy, not an arbitrary hash change.
- `worker`: lineage_id, worker_id, expected_epoch, active boolean. Rejects all human-profile/auth-user overlap, registers or advances the worker epoch and assignment, and stops/fences every lineage assigned to that worker.

Initial/reconnect order is explicit: bind or reconnect, register the worker if needed, resume sandbox controls, seed a fresh candidate, perform access-only identity observation, then install. Seeding while stopped is denied. Resume does not enable financial dispatch or establish provider identity.

## Worker boundary

`haven_finance_worker` is NOLOGIN, NOINHERIT, NOBYPASSRLS, not a member of authenticated/service roles, and has no table or Vault grants. The authenticating gateway must verify the signature and switch to this actual PostgreSQL role. The database independently checks role context plus claims: `role=haven_finance_worker`, UUID `sub`, UUID `hfa_org`, `iss=urn:haven:finance-worker:v1`, `aud=haven-finance-credentials`, exact purpose, positive worker_epoch, integer iat/exp with at most five-minute lifetime, and current active registry/assignment/epoch. Malformed fields are rejected before casts. Human organization/app_role/facility/version/app_metadata/user_metadata fields are forbidden.

The 329 pre-request function preserves existing human/anonymous/service behavior and permits only exact POST paths for the six worker RPCs (claim/start/capture/install/read-identity/observe-identity). All other tables, methods and RPC paths are denied for this role. Private implementations repeat authority checks; the gateway alone is insufficient. Actual issuer/key provisioning and verified PostgREST signature/role-routing behavior remain external gates. Workers must never receive project signing or service-role keys.

## Protected storage and uncertainty

Raw response strings are bounded to 64 KiB and stored through Vault 0.3.1 `create_secret(text,text,text,uuid)` only. Existing secrets are never updated. No plaintext values or raw response bodies are copied into public/haven metadata, audit history, ordinary receipts or returned error messages. A candidate contains only a private Vault UUID reference. Vault/API exceptions are sanitized and remain protected-store failures (SQLSTATE 55000); they do not create invalid-provider-response evidence. Only response parsing/shape failures are classified as invalid candidates. Database/server/transport logging, parameter logging and HTTP client error hygiene remain deployment/driver responsibilities; this migration cannot prove those external systems do not log credentials.

Installation validates access_token and refresh_token nonempty strings, bearer token type and positive integer expiry fields. A known hard expiry is retained across every revision of the same connection epoch: omission cannot erase it and a later returned deadline cannot extend it; an earlier deadline tightens it. Only explicit reconnect to a newer epoch can establish a new grant cap. Claim, start and installation enforce the preserved cap. Refresh expiry is anchored conservatively at the recorded start time; seed expiry is anchored at capture because no provider driver exists here. A real seed driver must supply only a newly obtained response and establish provider timing. Supplied environment labels are not proof: sandbox and production share Intuit's token endpoint. No blind refresh is offered to discover environment. The fixed-host access-only verification operation is the prerequisite; an immutable observation is still a trusted worker claim until actual provider execution is demonstrated. A disclosed bearer access token retains its provider scopes: SQL cannot restrict its external use to GET or the expected host. The future trusted driver must enforce method and egress restrictions; the lease is a database authority and metadata constraint, not a reduced-scope provider token.

A response lost after provider rotation but before durable capture remains a distributed unknown. A start response lost before the client receives its proof also remains unknown. Neither a new claim, worker reactivation, nor reconnect silently removes it. Trusted completion can retain an already-started known response but cannot install/read it. This deliberately sacrifices automatic recovery where evidence is missing.

All tables default to protected/fenced metadata and all release flags remain false. Restoring an active backup is not proven safe by schema flags alone: operators must fence connections and worker issuing/epochs before restoration is exposed, then complete provider/Vault reconciliation. There is no automatic restore attestation or production activation mechanism in 342.

## Local evidence boundary

The rollback-only native test refuses an existing Vault schema/extension, then creates a explicitly synthetic API stub and temporarily substitutes only the private availability checker. It proves transactions, states, ACLs, request checks and canary confinement; **it proves no encryption, real OAuth, issuer signature, hosted gateway, recovery or production safety**. The original checker fails closed when real Vault is absent. Test artifacts retain failures and exact hashes. No real credentials or production records are used.
