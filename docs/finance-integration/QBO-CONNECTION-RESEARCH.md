# QBO connection research and proposed recovery boundary

Checked **2026-09-09**, using public Intuit-authored documentation, SDK documentation/source and the official Intuit Developer publication. No provider API, credential exchange, subscription, account inspection or implementation was performed. QBO remains a reference adapter; **D01 product/company facts are pending**. This document does not establish a verified Haven company binding or authorize financial dispatch. [Intuit’s blog domain](https://blogs.intuit.com/) was verified to redirect to its `medium.com/intuitdev` publication; those cited articles are first-party sources.

## Verified facts and unresolved guarantees

| Area | Official evidence | Consequence / uncertainty |
|---|---|---|
| Refresh rotation | The current [Intuit JS client README](https://github.com/intuit/oauth-jsclient/blob/master/README.md#refresh-access_token) gives access tokens a 3,600-second lifetime, requires storing the latest returned refresh token, and says preceding refresh tokens expire 24 hours after a new one is received. | Store every returned token pair and expiry, even when the refresh-token string is unchanged. The README does not establish concurrent refresh ordering, guaranteed lost-response recovery, or provider fencing. |
| Conflicting older guidance | Intuit's [PHP authorization documentation](https://intuit.github.io/QuickBooks-V3-PHP-SDK/authorization.html#refreshing-oauth-2-0-token) describes daily rotation and forced expiration of the preceding token when it changes. | The published overlap descriptions conflict. Do not turn a presumed 24-hour grace interval into an automatic recovery guarantee, or claim every refresh necessarily returns a different string. |
| Hard expiry | The [official policy announcement](https://medium.com/intuitdev/important-changes-to-refresh-token-policy-8443779d40db), published 2025-11-12 and updated 2026-02-24, adds a five-year maximum. It identifies first accounting/payment-scope expirations in October 2028 and restricted/granular-scope expirations in February 2027; the reconnect URL setting is available. | The old rolling-100-day model is not indefinite authorization. Persist observed expiry fields; do not calculate an endless extension or infer an actual connection's grant date from these rollout dates. |
| Expiry field support | Current [JS OAuth source](https://github.com/intuit/oauth-jsclient/blob/master/src/OAuthClient.js) supports `includeRefreshTokenHardExpiresIn: true`, which sends `x-include-refresh-token-hard-expires-in: true`. The [Python guide](https://github.com/intuit/oauth-pythonclient/blob/master/docs/user-guide.rst) describes `x_refresh_token_hard_expires_in` when supplied. | Support both rolling and hard-expiry metadata, with missing hard expiry represented as unknown. SDK support is not proof that a particular app/token response includes it. |
| CloudEvents migration | The [official webhook announcement](https://medium.com/intuitdev/upcoming-change-to-webhooks-payload-structure-2a87dab642d0), published 2025-11-12 and updated 2026-05-05, extends the mandatory migration deadline to **2026-07-31**. Its example includes `specversion`, `id`, `source`, `type`, `intuitentityid`, `intuitaccountid`, `time`, and `data`. One request can contain multiple companies. | Build for CloudEvents. Do not infer any actual app's configured format. The sample time has **nine fractional digits**; preserve the raw provider timestamp instead of reusing Haven's six-digit PostgreSQL page-cursor schema. |
| Signature and identifiers | Intuit's [CloudEvents sample](https://github.com/IntuitDeveloper/SampleApp-Webhooks-Java-Cloudevents) verifies `intuit-signature` using HMAC-SHA256 and the webhook verifier token. Its [migration guide, Tasks 2.5–4](https://github.com/IntuitDeveloper/Prompt-Library/blob/main/workflows/webhooks-migration/prompt-template.md#task-25-idempotency) explicitly says an event's unique `id` is retained when the gateway retries a failed batch; it accepts `application/json` and `application/cloudevents+json`. | Stable provider event IDs support deduplication. Legacy entity IDs are not delivery IDs. A generated local UUID does not make legacy retries idempotent. Neither an event timestamp nor valid signature proves freshness, ordering, complete delivery or a financial-command outcome. |
| Catch-up | Intuit's [CDC guidance](https://medium.com/intuitdev/building-smarter-with-intuit-stay-in-sync-with-cdc-171f8094dd37), published 2023-08-24 and still available on the checked date, documents a **30-day** look-back and **1,000-object** response maximum. It returns current full objects, groups by entity type, places deleted objects after active objects, and recommends combining webhooks with periodic CDC. | CDC is bounded current-state reconciliation, not an immutable event log or full-history export. A response at the cap is potentially incomplete. The extracted exceptions list is missing; supported entity types still need confirmation. |

The main [OAuth guide](https://developer.intuit.com/app/developer/qbo/docs/develop/authentication-and-authorization/oauth-2.0), [OAuth FAQ](https://developer.intuit.com/app/developer/qbo/docs/develop/authentication-and-authorization/faq), and [webhook guide](https://developer.intuit.com/app/developer/qbo/docs/develop/webhooks) returned a compiling screen during this review. The [refresh-token support article](https://help.developer.intuit.com/s/article/Validity-of-Refresh-Token) returned a loading/CSS error; a browser attempt timed out. Their unseen contents are **not** verification evidence. Exact current webhook acknowledgment deadline, retry schedule/retention, ordering SLA, administrative replay window, and financial `requestid` retention/replay semantics remain unverified. No third-party explanations were adopted as provider guarantees. In particular, do not conflate authorization-code reuse behavior with refresh-token reuse behavior.

## Fixed hosts and company binding

The current [official OAuth client constants](https://github.com/intuit/oauth-jsclient/blob/master/src/OAuthClient.js) distinguish these endpoints:

| Purpose | Endpoint |
|---|---|
| QBO sandbox accounting | `https://sandbox-quickbooks.api.intuit.com/v3/company/{realmId}/…` |
| QBO production accounting | `https://quickbooks.api.intuit.com/v3/company/{realmId}/…` |
| Authorization, both environments | `https://appcenter.intuit.com/connect/oauth2` |
| Token exchange/refresh, both environments | `https://oauth.platform.intuit.com/oauth2/v1/tokens/bearer` |
| Revocation | `https://developer.api.intuit.com/v2/oauth2/tokens/revoke` |

Intuit's [getting-started example](https://intuitdeveloper.github.io/getstarted/) uses a company-scoped `GET /v3/company/{companyId}/companyinfo/{companyId}`. The SDK reads `realmId` from the OAuth callback; that assignment alone is not verification of the intended legal entity.

**Proposed binding check:** bind a single-use, expiring OAuth state to the current Haven actor, organization/entity, chosen environment, app registration, exact redirect URI and expected connection generation. Exchange the callback once, then use the resulting credential against the fixed environment host and independently expected realm. Validate the CompanyInfo response as a CompanyInfo object; retain a minimized identity attestation and its observation time. **Do not compare `CompanyInfo.Id` to the realm ID**, infer the realm from a company name, or treat successful OAuth user identity as company/legal-entity approval. Require separately reviewed D01 realm/company evidence; absent or mismatched evidence stays unverified. Never fall back from sandbox to production on error.

## Proposed common-engine contract

The following are engineering recommendations, not claims about implemented behavior or Intuit guarantees.

1. **Separate identity from secrets.** Immutable binding versions contain provider, environment, app registration, realm and Haven organization/entity, with capability/consent evidence. Secret revisions contain encrypted token pairs, observed expiry fields and key version. Routine credential rotation changes the secret revision; reconnect, realm/app/environment/scope changes require a new binding generation and invalidate dependent approvals. Public status exposes neither credentials nor arbitrary provider response bodies.

2. **One refresh operation per credential lineage.** Lock the shared credential authority across processes, re-read its revision, and durably reserve an attempt ID/fencing generation before issuing HTTP. Serialize reconnect/disconnect with the same authority. A local lease's expiry does not fence an already-running provider request: timeout or worker loss becomes `refresh_outcome_unknown`, not permission for another blind refresh. Require proof of worker termination/outcome reconciliation before any new exchange; do not hold business-period locks across HTTP.

3. **Persist before activation; preserve late candidates.** Durably seal a returned token pair as an immutable candidate tied to its exact attempt and input revision, then atomically activate it only if the binding/revision still matches. A failed compare-and-swap must retain the candidate in privileged quarantine and block unsafe recovery; discarding a late successful response might discard the only valid token. Reconnect/revocation must not silently delete unresolved candidates. Make secret persistence fail closed and ensure audit/telemetry never logs tokens, authorization headers, callback codes or full OAuth responses. The [official client README](https://github.com/intuit/oauth-jsclient/blob/master/README.md#retry-logic) advertises automatic retries and detailed logging, so those behaviors require explicit inspection/disablement in the pinned transport, not SDK-default trust.

4. **Acknowledge the irreducible crash gap.** No local database transaction can atomically commit with Intuit's token server. If the provider rotates and the sole response is lost before durable capture, the reviewed sources provide no mechanism guaranteed to recover it. Preserve the preceding encrypted revision, stop dependent work, classify uncertainty and offer controlled reauthorization if needed. A blanket promise that the integration can never lose authorization is unsupported. The enforceable promise is that it never knowingly discards a received candidate or masks an unknown refresh as success.

5. **Durable, authenticated webhook inbox.** Verify the signature over the original request representation before parsing or acknowledging; pin and independently test the exact SDK signature encoding with official fixtures before live use. Use durable uniqueness over app/environment plus provider `source`/event `id`, bind each event's `intuitaccountid` independently, and compare fingerprints on ID reuse. Duplicate acknowledgment is safe only after durable receipt. Unknown realms/types or conflicting bodies become controlled quarantine, never automatic new tenant bindings. Keep raw-body retention behind an explicit encryption/privacy policy; ordinary logs contain only minimized metadata. Acknowledge promptly after durable capture, process asynchronously, and treat webhook content as a hint requiring authoritative reads for financial reconciliation. Do not adopt sample in-memory storage or invented legacy event IDs as production durability.

6. **Catch-up with an explicit gap state.** Maintain per-binding/entity-type reconciliation checkpoints with overlap and independent periodic sweeps. Do not advance a coverage checkpoint through a capped response, an unsupported entity, an outage beyond the documented look-back, or unprocessed/deleted records. Splitting entity sets can reduce response volume, but `changedSince` is not a documented end-bounded pagination cursor; moving it forward until results shrink can silently skip older changes. Saturation/equal-time ties require a separately verified query/export strategy or manual reconciliation and remain `catch_up_incomplete`. Neither CDC nor webhook silence proves a timed-out write was absent.

7. **Keep unknown financial outcomes separate from retryable reads.** Preserve one immutable command identity, binding, exact payload/hash and provider request identity for any future write. A timeout, dropped connection, ambiguous 5xx, lost success receipt or credential failure after sending remains `financial_outcome_unknown`. Never generate a replacement request key or free source claims merely because the response was lost. Release requires an authoritative external-object match to the exact command, or a documented and tested provider replay/recovery contract. Amount/date similarity, successful token refresh, webhook receipt and a capped CDC miss are insufficient. Financial dispatch remains disabled while these semantics and F03/F05 business/privacy gates are open.

## Required proof before a live connection path

Confirm actual D01 product/app/environment/realm and responsible owner; document the permitted secret store/key lifecycle; verify current token overlap/concurrency/revocation behavior and hard-expiry fields with official support plus controlled sandbox evidence; test persistence failure and worker-loss boundaries; obtain signed CloudEvents fixtures and current retry/replay policy; test CDC saturation, tied timestamps, deletes and missing-history recovery; establish operation-specific write idempotency retention and authoritative reconciliation. These are remaining gates, not account facts or subscriptions requested by this research.
