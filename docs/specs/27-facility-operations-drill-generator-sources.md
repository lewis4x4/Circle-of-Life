## Existence is not finality

`drill_log` (220) has no lifecycle: a row exists or it does not. Migration 347 gives it one without declaring anything final: `record_version`, `finalized_at/by`, `version_recorded_at/by`, `entry_reason`, `correction_reason`, `voided_at/by`, `void_reason`, typed `readings`, `outcome` and `issue_summary`. Every existing row, and every row the emergency-preparedness page keeps writing, is a **draft** until a person finalizes it through `finalize_drill_log_review`. A final row refuses direct content changes and soft deletes; corrections go through `correct_drill_log_review` (a new version under the expected version and a reason) and voids through `void_drill_log_review`. A voided row is immutable. Hard deletes are refused.

Generator tests, carbon-monoxide checks and extinguisher currency checks had no table (the maintenance completion log cannot name which of two generators was observed). The new `asset_observations` table records one staff member's observation of one named asset, final by command only (`record_asset_observation_review`), with `basis` constrained to `staff_observed`: the command refuses `automatic_self_test` and `photo_only` by name. A controller log or a photo is supplementary evidence on the occurrence (COL-143), never a source record. Corrections and voids mirror the drill commands.

## A record satisfies exactly its occurrence, once, through 346

Each command commits one version and delivers it through the 346 mechanism in the same transaction under the caller's own session authority (request key `<key>:deliver`). The readers `haven.operation_source_read_drill_log` and `haven.operation_source_read_asset_observation` return the record's live state: `fire` → `hfo-al-m05-01`, `elopement` → `hfo-al-m06-01` (a tornado drill finalizes but has no checklist activity and is not delivered); `generator_test` → `hfo-al-w01-01`, `carbon_monoxide_check` → `hfo-al-w01-02`, `extinguisher_check` → `hfo-al-a07-03`; the facility or the asset as subject; the finalizer or corrector as recorder; `finalized_at` as the recording instant on every version so the late and future rules stay anchored on the original act (COL-145); the drill instant in the facility's timezone or `observed_at`; the conductor or observer as performer (`self` or `other_staff` with an on-behalf reason); typed `readings` passed verbatim as values, which satisfy only where an approved rule defines them; `pass`/`performed` or `fail`/`failed` with an issue whose summary the record carries. The commands enforce the late, on-behalf, future and failed-outcome rules up front, so a delivery is never refused for a reason the person could have stated.

Whether a record links is the delivery's verdict, returned as read and never hidden: `satisfied` or `corrected` (`linked: true`), `unmatched` when no rule or occurrence exists, `recorder_not_authorized` with attention when the finalizer is outside the published recorder list, `conflict` when a person or another record already satisfied the occurrence (a duplicate record is visible, never a second satisfaction), a recorded `statement_invalid` when the readings are not the rule's inputs. A failed observation opens a 341 issue bound to its receipt; a later void reverses the receipt, returns the occurrence to `pending`/`missed`, leaves the `invalidated` attention row and never closes the issue. A correction that moves the record to the other generator, or a drill to another period, invalidates the first occurrence's receipt and satisfies the second as a fresh chain, so one record never satisfies two. Review activities (`hfo-al-a07-01/02`, `hfo-al-a08-01/02`) are never allowlisted for any source: a log cannot satisfy its own review, which stays outstanding for a person.

## Idempotency, authority and reconciliation

Every command is keyed: `operation_source_record_requests` keeps one immutable row per request key with the reply as returned; a replay returns it with `replayed: true`, a different content or actor under the same key conflicts. Commands serialise on the request key, then on the record (finalize/correct/void), then on 346's per-record delivery lock, in the same order everywhere. A retired, deleted or moved asset refuses corrections and voids by name (the COL-133 retired-subject boundary), and a final drill log never changes between fire/elopement and tornado, so a delivered receipt is never stranded on an undeliverable record. Any managed actor with current site access may record, finalize, correct or void at that site (the operations roles COL-133 admits); satisfaction is decided by the governing rule's recorder list at delivery. Pending deliveries are reconciled only through the 346 `retry`/`select`/`dismiss` commands under the COL-133 broad operations scope.

## Legacy drill consumers

Five existing consumers encode five cadences (220 view rules ≥6 fire/≥2 elopement per year; 221 notification rule; 250 overdue thresholds; 125 quarterly/annual compliance tasks; 200 weekly review template) and none is Homewood's approved rule. This segment changes, reads and activates none of them; they keep counting drafts and finals alike until the approved rule retires them (`OWNER-DECISIONS.md` 3k).

## API

- `POST /api/admin/operations/asset-observations` — `{ request_key, payload: { facility_id, asset_id, observation_kind, observed_at, basis, observed_by?, outcome, readings?, issue_summary?, note?, entry_reason? } }` → `{ outcome: "record", record, delivery | null, linked, replayed }`.
- `GET /api/admin/operations/asset-observations?facility_id=&asset_id=&kind=&voided=` — the site's observations through the session, paged to exhaustion with the exact total.
- `POST /api/admin/operations/asset-observations/[id]` — `{ request_key, action: correct, expected_version, payload: { reason, … } }` or `{ request_key, action: void, payload: { reason } }`; a stale version returns `409` with `current_record_version`; a correction by someone other than the observer must carry `entry_reason` (it is recorded on behalf); a retired, deleted or moved asset refuses both by name.
- `POST /api/admin/operations/drill-logs/[id]` — `{ request_key, action: finalize, payload: { entry_reason? } }`, `correct` as above with drill fields (a final log never changes between fire/elopement and tornado), or `void`; a tornado drill returns `delivery: null, linked: false, link_reason: no_checklist_activity`; a voided log keeps its date/time slot, so a restatement is a correction.
