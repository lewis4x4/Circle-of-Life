# Facility operations subject-scoped occurrences — COL-139

Status: PARTIAL — HFO-04 foundation. September 10, 2026. Extends the [catalog](27-facility-operations-catalog.md), [current authority](27-facility-operations-authority.md), [applicability](27-facility-operations-applicability.md) and [evaluator](27-facility-operations-evaluator.md) contracts under BUILD-SCOPE section 5 (one evaluator, one occurrence per intended subject and period). This is source implementation: it confirms no schedule, enrols no real resident, employee or asset, generates no occurrence on any hosted project, sends no reminder, records no completion and establishes no hosted or operating acceptance.

## Identity

An occurrence is a row of `operation_task_instances` with a managed identity (`occurrence_kind` set). Its identity is **activity + site + typed subject + period key + shift** for scheduled work, **activity + site + subject + source event** for event work, and **activity + site + subject + request key** for manual unscheduled work. The template id, the requirement version id, the configuration id and the deadline are never part of the identity, so a revised template or configuration in the same period converges on the existing row and a moved deadline never mints a second one. The unique index `operation_occurrence_identity` is not filtered on status or `deleted_at`: a cancelled or soft-deleted occurrence keeps its identity and replay never recreates it. Legacy rows (`occurrence_kind` NULL) keep their template-keyed identity and every existing path; nothing reclassifies or remaps them.

Each occurrence pins the exact versions that governed it at a precise **governing instant** (`governing_at`: the due instant for scheduled work, the source event instant for event work, the creation instant for manual work). A same-day configuration cutover therefore chooses the version in force at the due instant, not at midnight. The evaluator output that produced the occurrence is persisted (`schedule_snapshot`: evaluator version, rule version, timezone, database-computed rule hash, occurrence date, inclusive period, due, grace end, reminder instant, DST adjustments) and is immutable, as are `period_key`, `period_start_date`, `period_end_date`, `governing_at`, `due_at`, `binding_id` and the source event columns. `occurrence_revision` is a database-generated fingerprint of the row's last update that clients echo back for optimistic reconciliation.

## Bindings

`operation_activity_bindings` is the explicit, effective-dated enrolment of one typed subject in one activity at one site with an `authority_class`, an optional shift, a provenance (`source` and `reason`) and the enrolling administrator. Registry existence and site configuration never enrol a resident, employee or asset. A binding is created only through `enroll_operation_binding_review` (owner, org_admin or facility_admin with a current site grant **and** the subject's current authority class) and closed only through `retire_operation_binding_review` or the service reconciliation. Its identity is immutable; only the closing columns can be set, once. The site itself (`subject_kind = facility`) needs no binding: the applicable, confirmed site configuration is the explicit enrolment of the site, and the generation command resolves or creates the site's one facility subject.

## Generation

`generate_operation_occurrences_service` is the only path that mints a scheduled or event identity, and only the service identity may call it. The identity guard admits a managed insert or update only when the transaction carries a token that the owner-run commands compute from the transaction id and an owner-only secret; the service identity, which keeps plain insert and update rights on the instance table for the legacy scheduler, cannot forge it. The scheduler evaluates the confirmed rule with the shared evaluator and sends the evaluator outputs plus the rule it evaluated; the database asserts the rule equals the stored one, that the evaluator version is known, that every item's date, period, due, grace and timezone are coherent, that the configuration and its central version were in force at each governing instant, expands each item to the subjects bound at that instant (or the facility subject), serialises by activity/site/subject with a transaction advisory lock, reports an incompatible overlap (different period key with overlapping periods, or a whole-day item against a shifted one) as a **conflict** without inserting, converges an exact duplicate with `ON CONFLICT DO NOTHING` and reports it as **existing**, and inserts the rest as `pending` with no performer, no completion and no evidence. Every item receives a truthful outcome: `created`, `existing`, `conflict`, `no_binding`, `binding_not_current`, `configuration_not_in_force` or `invalid`. Concurrent runs and retries therefore produce one row per intended subject and period; catch-up over past dates generates the historical periods under the versions that governed them and skips periods no version or binding covered.

`reconcile_operation_occurrences_service` is the narrow service reconciliation for native retirement or transfer: it closes open bindings whose subject is no longer current and cancels only `pending` occurrences whose period has not started, writing `reconciled` audit rows. It never touches in-progress, completed, missed or deferred rows, past or current periods, timestamps or evidence.

## Unscheduled, early and late work

`create_operation_manual_occurrence_review` records work that has no schedule or falls outside one. The row carries no period, no deadline and no grace; `assigned_shift_date` holds a labelled compatibility queue date (`schedule_snapshot.queue_date_is_compatibility_only = true`) that the legacy views need and that is never a compliance date. It snapshots the central version and site configuration in force at creation (a `needs_confirmation` schedule is expected; `not_applicable` refuses). The request key makes creation idempotent: a replay with the same payload returns the same row; a replay with a different payload is a conflict.

`associate_operation_occurrence_review` is the only way early, late or unknown-schedule work is connected to a scheduled occurrence. It is an immutable, audited relation (`operation_occurrence_associations`) with explicit one-to-one cardinality, the kind (`early`, `late`, `unscheduled`), the reason, the actor and the `occurrence_revision` the actor saw; a stale revision, a changed payload under the same request key, or work already associated elsewhere is a conflict. Association never rewrites either row's identity, snapshot, status or timestamps and implies no completion: the completion receipt is COL-142 and evidence transport is COL-143.

`cancel_operation_occurrence_review` cancels a managed occurrence under current authority with a reason and an idempotent request key, preserving its identity, snapshot, started time and every evidence column. Managed rows refuse the legacy defer and reinstate commands (they would create replacement rows without identity); legacy rows keep those commands unchanged. Service writes to managed rows outside the commands are refused by the identity guard.

## Scheduler and API

`oce-task-scheduler` keeps its legacy template pass with two compatibility corrections (existence keyed on the stable activity rather than the template id, and duplicate convergence on the legacy index) and skips a legacy template at a site where a confirmed applicable configuration for the same activity is in force. Its managed pass pages through every confirmed applicable configuration, evaluates only through the shared evaluator, reports invalid rules as unknown and `event` rules as awaiting their source (no production adapter exists), calls the generation command once per configuration, runs the reconciliation per facility, and returns per-run counts under `managed` without aborting when one configuration's command fails. Dry runs call no command.

Session routes under `/api/admin/operations/occurrences` (bindings list/enrol/retire, occurrence list, manual creation, association, cancellation) follow the COL-135 pattern: the current site grant is checked before any read or command, the actor is revalidated before every command, the database re-checks authority after locks, and errors are mapped without echoing internals. Reads go through the session client under the COL-133 subject boundaries, so another site's bindings, occurrences and associations are invisible.
